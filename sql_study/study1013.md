# RAG 챗봇 만들기 — LCEL 파이프라인으로 자동 연결하기

## 1. 오늘의 학습 목표

**핵심: 검색, 문서 정리, 프롬프트, LLM을 하나의 파이프라인으로 연결하여 RAG 챗봇을 완성한다.**

지금까지는 벡터 DB에서 문서를 검색하고, 검색 결과를 정리한 뒤, LLM에게 전달하는 과정을 각각 직접 실행했다.

오늘은 이 과정을 **LCEL(LangChain Expression Language)** 을 이용해 자동으로 연결한다.

### 지금까지 배운 내용

- **문서 분할(Chunking)**: 긴 문서를 작은 조각으로 나누어 필요한 부분만 검색한다.
- **임베딩(Embedding)**: 문서와 질문의 의미를 벡터로 표현하여 의미적으로 관련된 내용을 찾는다.
- **벡터 DB(Vector Database)**: 문서의 벡터를 저장하고 유사한 내용을 검색한다.
- **LLM**: 검색된 문서를 참고하여 사용자의 질문에 답변한다.

### 오늘 배울 내용

- **Retriever(검색기)**: 질문을 받아 관련 문서를 검색하는 표준 인터페이스
- **`format_docs()`**: 검색된 여러 문서를 하나의 문자열로 정리하는 함수
- **LCEL 파이프라인**: 검색부터 답변 생성까지의 과정을 하나로 연결하는 방법

---

## 2. RAG의 전체 동작 원리

RAG는 사용자의 질문과 관련된 문서를 먼저 검색하고, 검색 결과를 참고하여 LLM이 답변하도록 만드는 방식이다.

### 2-1. RAG의 5단계 흐름

1. **질문 입력**: 사용자가 질문한다.
2. **문서 검색**: 검색기가 벡터 DB에서 관련 청크를 찾는다.
3. **문서 정리**: 검색된 청크들을 하나의 문자열로 합치고 출처를 표시한다.
4. **프롬프트 구성**: 정리한 문서와 원래 질문을 LLM에게 전달한다.
5. **답변 생성**: LLM이 전달받은 자료를 참고하여 답변한다.

예를 들어 사용자가 다음과 같이 질문했다고 가정하자.

> 개봉한 원두도 환불할 수 있나요?

RAG 챗봇은 환불 관련 문서를 검색하고, 검색된 내용과 질문을 함께 LLM에게 전달한다. LLM은 전달받은 자료를 바탕으로 답변을 생성한다.

**중요:** 검색 결과에 정답이 없거나 근거가 부족할 수 있다. 따라서 프롬프트에서 근거가 부족할 때는 모른다고 답하도록 지시해야 한다. RAG를 사용한다고 해서 답변의 정확성이 자동으로 보장되는 것은 아니다.

## 3. 새 부품 ① — 검색기(Retriever)

### 3-1. 기존 방식: 벡터 DB에서 직접 검색하기

지금까지는 다음과 같이 벡터 DB의 검색 함수를 직접 호출했다.

```python
# 질문과 의미적으로 유사한 문서 3개를 검색한다.
results = db.similarity_search("환불 규정 알려줘", k=3)
```

- `db`: 문서가 저장된 벡터 DB
- `similarity_search()`: 질문과 유사한 문서를 검색하는 메서드
- `"환불 규정 알려줘"`: 검색에 사용할 질문
- `k=3`: 검색 결과를 최대 3개 가져오도록 지정

이 방식도 정상적으로 작동한다. 하지만 LCEL 파이프라인에 검색 단계를 연결하려면 검색 기능을 일관된 인터페이스로 다룰 수 있는 **Retriever** 를 사용하는 편이 편리하다.

### 3-2. Retriever란?

**Retriever는 질문을 받아 관련 문서를 반환하는 검색 인터페이스다.**

기존에는 벡터 DB의 검색 메서드를 직접 호출했다면, 이제는 Retriever를 통해 문서를 검색할 수 있다.

```python
# 벡터 DB를 검색기로 변환한다.
retriever = db.as_retriever(
    search_kwargs={"k": 3}  # 검색 결과를 최대 3개 가져오도록 설정한다.
)

# 질문을 전달하여 관련 문서를 검색한다.
results = retriever.invoke("환불 규정 알려줘")
```

코드의 의미를 하나씩 살펴보자.

- `db.as_retriever()`: 벡터 DB를 Retriever 인터페이스로 변환한다.
- `search_kwargs={"k": 3}`: 검색할 때 사용할 옵션을 지정한다.
- `retriever.invoke(question)`: 질문을 입력하여 관련 문서 목록을 반환받는다.

여기서 `invoke()`는 입력값을 전달하여 실행하는 메서드다. Retriever에서는 질문을 입력하면 검색된 `Document` 객체 목록이 반환된다.

### 3-3. 벡터 DB와 Retriever의 차이

| 구분 | 역할 |
|---|---|
| 벡터 DB (`db`) | 문서의 벡터를 저장하고 유사도 검색을 수행한다. |
| Retriever (`retriever`) | 질문을 받아 관련 문서를 반환하는 표준 인터페이스다. |
| `invoke()` | Retriever에 질문을 전달하고 검색 결과를 받는다. |

비유하면 다음과 같다.

- **벡터 DB**: 책이 정리되어 있는 서고
- **Retriever**: 필요한 책을 찾아주는 사서
- **질문**: 사서에게 전달하는 요청

사용자는 서고의 내부 구조를 직접 다루지 않고 사서에게 요청하듯이 Retriever에 질문을 전달하면 된다.

**핵심 정리:** Retriever는 벡터 DB를 대체하는 것이 아니라, 검색 기능을 파이프라인에서 편리하게 사용하도록 감싸는 인터페이스다.

## 4. 새 부품 ② — 청크 정리 함수(`format_docs`)

### 4-1. 왜 문서를 합쳐야 할까?

Retriever가 반환하는 검색 결과는 하나의 긴 문자열이 아니라 여러 개의 `Document` 객체로 구성된다.

각 `Document`에는 주로 다음 정보가 들어 있다.

- `page_content`: 실제 문서 내용
- `metadata`: 출처 파일명이나 문서 분류 등 부가 정보

예를 들어 다음과 같이 검색 결과가 반환될 수 있다.

```python
# 검색 결과에 포함된 문서의 예시를 만든다.
docs = [
    Document(
        page_content="개봉한 원두는 환불이 불가능합니다.",
        metadata={"source": "02_refund.md"}
    ),
    Document(
        page_content="환불은 수령 후 7일 이내 신청해야 합니다.",
        metadata={"source": "02_refund.md"}
    ),
    Document(
        page_content="상품별 환불 조건을 확인하세요.",
        metadata={"source": "01_faq.md"}
    ),
]
```

LLM에게 검색 결과를 전달하려면 각 문서의 내용을 하나의 문자열로 합치는 작업이 필요하다. 이때 출처까지 함께 정리하면 답변의 근거를 확인하기가 더 쉽다.

### 4-2. `format_docs()` 함수 만들기

```python
# 검색된 문서들을 하나의 문자열로 합치는 함수를 정의한다.
def format_docs(docs):
    # 각 문서의 출처와 내용을 문자열로 만든다.
    formatted_docs = [
        f"[출처: {doc.metadata.get('source', '출처 미상')}]\n{doc.page_content}"
        for doc in docs
    ]

    # 각 문서 사이에 빈 줄을 넣어 하나의 문자열로 합친다.
    return "\n\n".join(formatted_docs)
```

#### 코드 한 줄씩 이해하기

**① `def format_docs(docs):`**

- `format_docs`라는 함수를 정의한다.
- `docs`는 Retriever가 반환한 여러 `Document` 객체의 목록이다.

**② `doc.metadata.get('source', '출처 미상')`**

- `metadata`에서 `source` 값을 가져온다.
- `source`가 없으면 기본값인 `출처 미상`을 사용한다.
- `.get()`을 사용하면 해당 키가 없을 때 오류가 발생하는 것을 방지할 수 있다.

**③ `doc.page_content`**

- 문서에 저장된 실제 텍스트 내용을 가져온다.

**④ `"\n\n".join(formatted_docs)`**

- 여러 문자열을 빈 줄 두 개에 해당하는 줄바꿈으로 연결한다.
- 최종 결과는 하나의 문자열이 된다.

### 4-3. 실행 결과 확인하기

```python
# 앞에서 만든 문서 목록을 하나의 문자열로 정리한다.
context = format_docs(docs)

# 정리된 문자열을 출력한다.
print(context)
```

출력 결과는 다음과 같은 형태가 된다.

```
[출처: 02_refund.md]
개봉한 원두는 환불이 불가능합니다.

[출처: 02_refund.md]
환불은 수령 후 7일 이내 신청해야 합니다.

[출처: 01_faq.md]
상품별 환불 조건을 확인하세요.
```

**핵심 정리:** `format_docs()`는 검색된 여러 문서의 내용과 출처를 하나의 문자열로 정리하여 LLM에게 전달하기 위한 함수다.

## 5. 새 부품 ③ — LCEL 파이프라인

### 5-1. LCEL이란?

**LCEL(LangChain Expression Language)은 LangChain의 여러 구성 요소를 연결하여 하나의 실행 흐름을 만드는 표현 방식이다.**

LCEL에서는 `|` 기호를 사용해 앞 단계의 출력을 다음 단계의 입력으로 전달할 수 있다.

```python
# 프롬프트를 만들고 LLM과 연결한다.
chain = prompt | llm
```

위 코드는 프롬프트의 실행 결과를 LLM에 전달하는 체인을 만든다.

RAG에서는 이 앞에 검색과 문서 정리 단계를 추가하면 된다.

### 5-2. LCEL의 `|` 기호 이해하기

일반적인 파이프라인의 개념은 다음과 같다.

```
입력 → 단계 A → 단계 B → 단계 C → 최종 출력
```

LCEL에서는 다음처럼 표현할 수 있다.

```python
# A의 출력이 B의 입력으로 전달되고, B의 출력이 C의 입력으로 전달된다.
chain = A | B | C
```

이때 `|`는 단순한 텍스트 구분 기호가 아니라 LCEL 구성 요소들을 연결하는 연산자다.

### 5-3. `RunnablePassthrough()`란?

RAG에서는 검색을 위해 질문을 사용하면서도, 원래 질문을 프롬프트에 그대로 전달해야 한다.

`RunnablePassthrough()`는 입력값을 변경하지 않고 그대로 다음 단계에 전달하는 Runnable이다.

```python
# 입력된 질문을 변경하지 않고 그대로 전달하는 구성 요소를 만든다.
question_passthrough = RunnablePassthrough()

# 질문을 그대로 전달하여 결과를 확인한다.
question = "개봉한 원두도 환불할 수 있나요?"
result = question_passthrough.invoke(question)

# 입력값과 같은 질문이 출력된다.
print(result)
```

출력:

```
개봉한 원두도 환불할 수 있나요?
```

RAG에서는 다음 두 작업이 동시에 필요하다.

- `context`: 질문을 검색기에 전달하고, 검색된 문서를 문자열로 정리한다.
- `question`: 원래 질문을 변경하지 않고 그대로 전달한다.

따라서 LCEL의 딕셔너리 형태를 활용해 두 값을 준비한다.

```python
# 질문을 검색 및 문서 정리 과정에 전달한다.
# 동시에 원래 질문도 별도의 question 값으로 유지한다.
rag_inputs = {
    "context": retriever | format_docs,
    "question": RunnablePassthrough(),
}
```

이 딕셔너리는 두 가지 값을 만드는 흐름을 정의한다. `context`에는 검색 후 정리된 문자열이 들어가고, `question`에는 원래 질문이 들어간다.

## 6. RAG 프롬프트 구성하기

검색된 문서를 참고하여 답변하도록 LLM에게 명확한 지침을 제공해야 한다.

```python
# 프롬프트 템플릿을 생성한다.
rag_prompt = ChatPromptTemplate.from_template(
    """
    당신은 위니브 카페 고객 상담 챗봇입니다.

    아래 제공된 참고 문서를 바탕으로 질문에 답변하세요.
    참고 문서에 없는 내용은 추측하지 말고, 확인할 수 없다고 안내하세요.
    답변의 근거가 되는 출처가 있다면 함께 표시하세요.

    [참고 문서]
    {context}

    [사용자 질문]
    {question}

    [답변]
    """
)
```

### 프롬프트의 핵심 요소

- `{context}`: 검색된 문서를 정리한 문자열이 들어가는 자리
- `{question}`: 사용자가 입력한 원래 질문이 들어가는 자리
- 근거가 부족하면 추측하지 말라는 지침
- 가능한 경우 출처를 함께 안내하라는 지침

`{context}`와 `{question}`은 실행할 때 실제 값으로 채워진다.

**주의:** 프롬프트에 출처를 표시하라고 지시해도 LLM이 출처를 잘못 붙일 가능성은 있다. 실제 서비스에서는 검색 결과의 출처 정보를 별도로 추적하고, 답변과 근거가 일치하는지 평가하는 것이 좋다.

## 7. 최종 완성 — RAG 파이프라인 연결하기

이제 지금까지 만든 부품들을 하나로 연결한다.

```python
# 질문을 검색하고, 검색 결과를 정리한 뒤, LLM 답변까지 연결한다.
rag_chain = (
    {
        # 질문으로 관련 문서를 검색하고, 문서 내용을 하나의 문자열로 정리한다.
        "context": retriever | format_docs,

        # 원래 질문을 변경하지 않고 그대로 전달한다.
        "question": RunnablePassthrough(),
    }
    # 정리된 문서와 원래 질문을 프롬프트에 넣는다.
    | rag_prompt

    # 완성된 프롬프트를 LLM에 전달하여 답변을 생성한다.
    | llm

    # AI 응답 객체에서 답변 텍스트만 추출한다.
    | StrOutputParser()
)
```

### 7-1. 파이프라인 흐름 이해하기

```
사용자 질문
    │
    ├── context 경로
    │      │
    │      ▼
    │   Retriever
    │      │
    │      ▼
    │   관련 문서 검색
    │      │
    │      ▼
    │   format_docs()
    │      │
    │      ▼
    │   정리된 참고 문서 ─────────┐
    │                             │
    └── question 경로             │
           │                      │
           ▼                      │
      원래 질문 유지 ─────────────┤
                                  ▼
                              rag_prompt
                                  │
                                  ▼
                                 LLM
                                  │
                                  ▼
                           StrOutputParser()
                                  │
                                  ▼
                             최종 답변
```

### 7-2. 각 구성 요소의 역할

| 구성 요소 | 역할 |
|---|---|
| `retriever` | 질문과 관련된 문서를 검색한다. |
| `format_docs` | 검색된 문서의 내용과 출처를 문자열로 정리한다. |
| `RunnablePassthrough()` | 원래 질문을 변경하지 않고 전달한다. |
| `rag_prompt` | 참고 문서와 질문을 LLM에 전달할 형식으로 구성한다. |
| `llm` | 참고 문서를 바탕으로 답변을 생성한다. |
| `StrOutputParser()` | AI 응답 객체에서 텍스트를 추출한다. |

`StrOutputParser()`를 사용하면 다음 단계에서 답변 텍스트를 편리하게 다룰 수 있다.

## 8. RAG 챗봇 실행하기

파이프라인을 만들었다면 이제 질문 하나만 전달해 전체 흐름을 실행할 수 있다.

```python
# 사용자가 입력한 질문을 준비한다.
question = "개봉한 원두도 환불할 수 있나요?"

# 질문을 RAG 파이프라인에 전달하고 답변을 생성한다.
answer = rag_chain.invoke(question)

# 생성된 답변을 출력한다.
print(answer)
```

이 한 번의 `invoke()` 호출 안에서 다음 작업이 연결되어 실행된다.

1. 질문으로 관련 문서를 검색한다.
2. 검색된 문서와 출처를 정리한다.
3. 정리된 문서와 원래 질문을 프롬프트에 넣는다.
4. LLM이 답변을 생성한다.
5. 답변 텍스트를 반환한다.

**중요:** 이 코드는 기존 학습 환경에서 `db`, `retriever`, `Document`, `ChatPromptTemplate`, `RunnablePassthrough`, `llm`, `StrOutputParser` 등이 준비되어 있다는 전제다. 앞 단계에서 사용한 변수 이름과 현재 코드의 변수 이름이 다르면 일치시켜야 한다.

## 9. 오늘의 핵심 정리

### 새롭게 배운 세 가지

1. **Retriever**: 질문을 받아 관련 문서를 반환하는 검색 인터페이스
2. **`format_docs()`**: 여러 문서의 내용과 출처를 하나의 문자열로 정리하는 함수
3. **LCEL 파이프라인**: 검색부터 답변 생성까지의 단계를 하나로 연결하는 방식

### 반드시 이해해야 할 코드

```python
# context에는 검색된 문서를 정리한 결과를 넣는다.
# question에는 원래 질문을 그대로 넣는다.
rag_chain = (
    {
        "context": retriever | format_docs,
        "question": RunnablePassthrough(),
    }
    | rag_prompt
    | llm
    | StrOutputParser()
)
```

이 코드의 핵심은 **질문 하나를 입력하면 검색, 문서 정리, 프롬프트 구성, 답변 생성이 연결되어 실행된다**는 것이다.

### 복습 질문

**Q1. Retriever를 사용하는 이유는 무엇인가?**

벡터 DB의 검색 기능을 일관된 인터페이스로 다루고 LCEL 파이프라인에 편리하게 연결하기 위해서다.

**Q2. `format_docs()`가 필요한 이유는 무엇인가?**

검색 결과인 여러 `Document` 객체의 내용을 하나의 문자열로 정리하고 출처도 함께 전달하기 위해서다.

**Q3. `RunnablePassthrough()`의 역할은 무엇인가?**

원래 질문을 변경하지 않고 다음 단계로 전달한다.

**Q4. `retriever | format_docs`는 어떤 의미인가?**

질문을 검색기에 전달하여 관련 문서를 찾고, 그 결과를 `format_docs()`로 정리하는 흐름이다.

**Q5. RAG 파이프라인을 만들면 무엇이 편리해지는가?**

검색, 문서 정리, 프롬프트 구성, 답변 생성을 각각 수동으로 실행하지 않고 하나의 체인으로 연결해 실행할 수 있다.

## 10. 한 문장으로 기억하기

**RAG는 Retriever로 관련 문서를 검색하고, `format_docs()`로 정리한 뒤, LCEL 파이프라인을 통해 질문과 함께 LLM에 전달하여 답변을 생성하는 구조다.**
