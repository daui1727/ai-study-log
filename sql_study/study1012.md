# 5. RAG 기반 AI 서비스

## 5-1. RAG란 무엇이고, 왜 필요한가?

### 1. 학습 목표

- LLM이 환각(Hallucination)을 일으키는 이유를 이해한다.
- RAG가 필요한 이유와 기본 구조를 이해한다.
- 프롬프트에 외부 문서를 전달하여 답변의 근거로 활용하는 원리를 이해한다.
- LangChain의 `Prompt`, `LLM`, `Parser`가 어떤 역할을 하는지 이해한다.

---

### 2. RAG가 필요한 이유: LLM의 환각(Hallucination)

#### 2-1. 문제 상황

나뭇잎 카페 고객센터에 다음과 같은 문의가 들어왔다고 가정한다.

**고객 질문**

> 지난주에 구입한 원두를 개봉해서 한 번 내려 마셨는데, 입맛에 맞지 않습니다. 환불되나요?

**잘못된 챗봇 답변**

> 구매일로부터 30일 이내라면 개봉한 원두도 전액 환불 가능합니다.

하지만 실제 환불 정책은 다음과 같다.

**실제 환불 정책**

- 개봉한 원두 및 드립백: 식품 위생상 재판매가 불가능하므로 환불 불가
- 미개봉 상품: 7일 이내 반품 가능

챗봇은 친절하게 답변했지만, 실제 규정을 확인하지 않고 잘못된 정보를 제공했다.

이처럼 AI 서비스에서는 답변의 자연스러움뿐 아니라 **답변의 정확성과 근거**가 중요하다.

#### 2-2. 환각(Hallucination)이란?

환각은 LLM이 사실과 다르거나 근거가 부족한 정보를 그럴듯하게 생성하는 현상이다.

LLM은 학습한 언어 패턴을 바탕으로 문장을 생성한다. 따라서 항상 사실을 검증하거나 최신 정보를 확인한 뒤 답변하는 것은 아니다.

예를 들어 다음과 같은 차이가 있다.

| 질문 | LLM의 한계 |
|---|---|
| 물은 몇 도에서 끓는가? | 일반적인 학습 지식을 바탕으로 답변할 수 있다. |
| Python에서 리스트를 어떻게 정렬하는가? | 학습한 프로그래밍 지식을 바탕으로 답변할 수 있다. |
| 우리 회사의 비공개 환불 규정은 무엇인가? | 해당 규정에 접근할 수 없다면 정확한 답변을 보장할 수 없다. |

특히 회사 내부 규정, 최신 상품 정보, 고객 주문 내역처럼 외부에 공개되지 않았거나 변경될 수 있는 정보는 별도의 데이터 조회가 필요하다.

#### 2-3. 환각이 실제 서비스에 미치는 영향

| 잘못된 안내 | 발생할 수 있는 문제 |
|---|---|
| 개봉한 원두도 환불 가능 | 환불 분쟁 및 금전적 손실 |
| 배송비는 항상 무료 | 결제 관련 고객 불만 |
| 새벽 배송 가능 | 배송 약속 불이행 및 신뢰 하락 |

**핵심:** 실제 서비스에서는 LLM이 모르는 정보를 추측하게 두기보다, 신뢰할 수 있는 자료를 제공하고 그 자료를 근거로 답변하도록 설계해야 한다.

### 3. 해결책: RAG

#### 3-1. RAG의 의미

RAG는 `Retrieval-Augmented Generation`의 약자다.

| 구성 요소 | 의미 | 역할 |
|---|---|---|
| Retrieval | 검색 | 질문과 관련된 정보를 찾는다. |
| Augmented | 보강 | 검색한 정보를 LLM의 입력에 추가한다. |
| Generation | 생성 | LLM이 제공된 정보를 활용해 답변을 생성한다. |

쉽게 말하면, **AI가 답변하기 전에 필요한 문서를 찾아 읽고, 그 내용을 근거로 답변하도록 만드는 방식**이다.

#### 3-2. LLM 단독 방식과 RAG 비교

**LLM 단독 방식**

```
사용자 질문
    ↓
LLM
    ↓
답변 생성
```

LLM이 가진 기존 지식에 의존한다. 필요한 정보가 없거나 불확실한 경우 잘못된 답변을 생성할 수 있다.

**RAG 방식**

```
사용자 질문
    ↓
관련 문서 검색
    ↓
검색 결과를 질문과 함께 전달
    ↓
LLM
    ↓
근거 기반 답변
```

RAG는 LLM 자체를 다시 학습시키는 대신, 답변에 필요한 외부 정보를 입력에 추가한다.

단, RAG를 적용한다고 환각이 완전히 사라지는 것은 아니다. 검색 결과가 부정확하거나 관련 정보가 없을 경우에는 여전히 잘못된 답변이 나올 수 있다.

#### 3-3. RAG가 필요한 대표적인 상황

- 사내 문서 기반 질의응답
- 고객센터 상담 챗봇
- 상품 및 환불 정책 안내
- 매뉴얼 검색 시스템
- 계약서 및 보고서 질의응답
- 창고관리 시스템의 업무 규정 검색

공통점은 **LLM의 일반 지식만으로는 부족하고, 특정 문서나 데이터에 근거한 답변이 필요하다**는 것이다.

---

### 4. 가장 단순한 RAG 이해하기

일반적인 RAG는 질문과 관련된 문서의 일부를 검색해서 LLM에 전달한다.

하지만 처음부터 검색 시스템을 구현하면 이해해야 할 개념이 많아진다. 따라서 먼저 문서 전체를 프롬프트에 넣는 단순한 방식으로 원리를 익힐 수 있다.

**단순 RAG**

```
질문 + 문서 전체
        ↓
       LLM
        ↓
      답변
```

**일반적인 RAG**

```
사용자 질문
    ↓
질문과 관련된 문서 검색
    ↓
관련 문서 일부만 추출
    ↓
질문 + 검색 결과
    ↓
LLM
    ↓
답변
```

단순 RAG는 문서를 통째로 전달하므로 구현하기 쉽지만, 문서가 커질수록 토큰 사용량과 처리 비용이 증가한다.

일반적인 RAG는 필요한 부분만 검색하여 전달하기 때문에 대량의 문서를 다루는 데 더 적합하다.

---

### 5. RAG 구현에 필요한 LangChain 구성 요소

#### 5-1. LLM: 답변을 생성하는 모델

```python
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(
    model="gpt-4o-mini",
    temperature=0
)

answer = llm.invoke("질문")
```

- `ChatOpenAI`: OpenAI의 채팅 모델을 LangChain에서 사용하기 위한 클래스
- `model`: 사용할 모델 지정
- `temperature`: 응답 생성의 무작위성에 영향을 주는 설정
- `invoke()`: 입력을 전달하고 결과를 반환하는 메서드

`temperature=0`은 응답의 무작위성을 낮추기 위한 설정이다. 다만 항상 완전히 동일한 결과나 정확한 답변을 보장하지는 않는다.

실제 코드를 실행하려면 별도의 API 인증 설정이 필요하다.

#### 5-2. Prompt: LLM에게 전달할 지시문

프롬프트는 LLM에게 역할, 규칙, 참고 자료 및 질문을 전달하는 입력 형식이다.

예를 들어 고객센터 챗봇에는 다음과 같은 규칙을 줄 수 있다.

```
당신은 나뭇잎 카페 고객센터 상담원입니다.

아래 제공된 규정 문서를 근거로 답변하세요.
문서에 없는 내용은 임의로 추측하지 말고,
확인할 수 없다고 안내하세요.

[규정 문서]
{document}

[고객 질문]
{question}
```

여기서 `{document}`는 규정 문서가 들어갈 자리이고, `{question}`은 사용자의 질문이 들어갈 자리다.

질문이 들어올 때마다 해당 변수에 서로 다른 값을 전달할 수 있다.

**핵심:** 문서를 입력에 포함하는 것뿐 아니라, 문서에 없는 내용을 추측하지 않도록 지시하는 것도 중요하다.

#### 5-3. Parser: 결과를 원하는 형태로 변환

```python
chatbot = prompt | llm | parser
```

각 구성 요소의 역할은 다음과 같다.

```
prompt
  ↓
LLM에 전달할 입력 구성

llm
  ↓
답변 생성

parser
  ↓
결과를 원하는 형식으로 변환
```

`|`는 LangChain에서 Runnable 구성 요소를 연결하는 파이프 연산자다.

실제로 사용할 파서는 결과 형식에 따라 달라진다. 예를 들어 문자열로 변환하려면 `StrOutputParser`를 사용할 수 있다.

```python
from langchain_core.output_parsers import StrOutputParser

parser = StrOutputParser()

chatbot = prompt | llm | parser
```

### 6. 단순 RAG의 핵심 구현 예제

다음 코드는 환불 정책 문서를 프롬프트에 직접 전달하는 간단한 예제다.

```python
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

prompt = ChatPromptTemplate.from_messages([
    (
        "system",
        """당신은 나뭇잎 카페 고객센터 상담원입니다.
        아래 제공된 규정 문서를 근거로 답변하세요.
        문서에 없는 내용은 추측하지 말고,
        확인할 수 없다고 안내하세요.

        [규정 문서]
        {document}"""
    ),
    ("human", "{question}")
])

parser = StrOutputParser()

rag_chain = prompt | llm | parser

document = """
개봉한 원두 및 드립백은 환불할 수 없습니다.
미개봉 상품은 7일 이내 반품 가능합니다.
"""

result = rag_chain.invoke({
    "document": document,
    "question": "개봉한 원두도 환불할 수 있나요?"
})

print(result)
```

**코드의 실행 흐름**

1. `document` 변수에 환불 규정을 저장한다.
2. 사용자의 질문을 `question`에 전달한다.
3. `prompt`가 규정과 질문을 포함한 입력을 구성한다.
4. `llm`이 입력을 바탕으로 답변을 생성한다.
5. `parser`가 결과를 문자열로 변환한다.
6. `print()`로 최종 답변을 출력한다.

이 예제는 문서를 직접 전달하는 방식이므로, 아직 문서 검색이나 벡터 DB는 사용하지 않는다.

### 7. RAG의 한계와 주의사항

RAG는 환각을 줄이는 데 도움이 되지만 모든 문제를 해결하지는 않는다.

- **검색 실패:** 필요한 문서를 찾지 못할 수 있다.
- **문서 품질 문제:** 문서 자체에 오류나 오래된 정보가 있을 수 있다.
- **문맥 부족:** 검색한 문서 일부만으로는 답변하기 어려울 수 있다.
- **모델의 오해:** LLM이 제공된 내용을 잘못 해석할 수 있다.
- **토큰 제한 및 비용:** 문서가 너무 길면 처리 비용이 증가하거나 입력 한도를 초과할 수 있다.

따라서 실제 서비스에서는 검색 품질, 문서 최신성, 답변의 근거 및 예외 상황을 함께 관리해야 한다.

### 8. 오늘의 핵심 용어

| 용어 | 정리 |
|---|---|
| LLM | 대량의 데이터로 학습하여 자연어를 이해하고 생성하는 대규모 언어 모델 |
| Hallucination | 사실과 다르거나 근거가 부족한 정보를 그럴듯하게 생성하는 현상 |
| RAG | 외부 정보를 검색하고 LLM 입력에 추가하여 답변을 생성하는 방식 |
| Retrieval | 질문과 관련된 정보를 검색하는 단계 |
| Augmented | 검색한 정보를 모델 입력에 추가하는 단계 |
| Generation | LLM이 답변을 생성하는 단계 |
| Prompt | LLM에 전달하는 지시문과 입력 형식 |
| Temperature | 모델 응답의 무작위성에 영향을 주는 설정 |
| Token | 모델이 입력과 출력을 처리할 때 사용하는 텍스트 단위 |
| Parser | 모델 결과를 필요한 형식으로 변환하는 구성 요소 |
| LangSmith | LangChain 기반 애플리케이션의 실행 추적과 디버깅 등을 지원하는 도구 |

### 9. 오늘의 학습 정리

**핵심 결론**

RAG는 LLM에게 필요한 외부 정보를 제공하여, 해당 정보를 근거로 답변하도록 만드는 방법이다.

오늘 이해해야 할 흐름은 다음과 같다.

```
LLM 단독 사용의 한계
        ↓
환각 문제
        ↓
신뢰할 수 있는 문서 제공
        ↓
프롬프트에 문서와 질문 전달
        ↓
LLM이 문서를 근거로 답변
        ↓
RAG의 기본 원리 이해
```

# [ RAG 기초 ① 문서를 불러오고 잘게 쪼개기 ]

## 1. 왜 문서를 미리 준비해야 할까?

지난 실습에서는 문서 전체를 프롬프트에 넣어 챗봇이 문서에 근거해 답변하도록 만들었다. 문서가 적을 때는 괜찮지만, 사내 규정이나 기술 매뉴얼이 수십 개라면 매번 모든 문서를 넣는 것은 비효율적이다.

- **문제 ①** 문서가 길수록 입력 토큰과 비용이 증가한다.
- **문제 ②** 질문과 관련 없는 내용까지 모델에 전달된다.
- **문제 ③** 모델이 한 번에 처리할 수 있는 입력 길이에도 한계가 있다.

따라서 문서를 미리 작은 단위로 나누고, 질문이 들어오면 **관련 있는 부분만 검색해서 LLM에 전달**한다.

이것이 RAG 시스템을 구성하는 중요한 준비 과정이다.

## 2. 문서 불러오기 — Document Loader

파일은 컴퓨터에 저장되어 있지만, 프로그램이 내용을 처리하려면 먼저 파일을 읽어야 한다.

**Document Loader**는 파일을 읽어 프로그램에서 다룰 수 있는 `Document` 객체로 변환한다.

`Document`에는 크게 두 가지 정보가 있다.

| 구성 요소 | 의미 | 예시 |
|---|---|---|
| `page_content` | 문서의 실제 본문 | "반품은 수령일로부터 7일 이내 신청 가능합니다." |
| `metadata` | 문서에 관한 부가 정보 | `source`, `category` |

예를 들어 `source`에는 파일명이나 문서 출처를, `category`에는 환불·배송 등의 분류를 저장할 수 있다.

이 메타데이터는 나중에 **검색 결과의 출처를 표시하거나 특정 분류의 문서만 검색할 때** 활용한다.

## 3. 문서 쪼개기 —  Splitter

문서를 불러왔다면 검색하기 좋은 크기로 나눈다. 이때 잘린 각각의 조각을 **청크(Chunk)**라고 한다.

청킹이 필요한 이유는 두 가지다.

1. 질문과 관련 있는 작은 부분을 검색하기 쉽다.
2. LLM에 필요한 정보만 전달해 입력 길이와 비용을 관리할 수 있다.

### 청킹을 조절하는 두 가지 설정

| 설정 | 의미 | 특징 |
|---|---|---|
| `chunk_size` | 청크 하나의 목표 크기 | 너무 작으면 맥락이 끊기고, 너무 크면 검색이 부정확해질 수 있음 |
| `chunk_overlap` | 인접한 청크끼리 겹치는 내용의 크기 | 문장이나 핵심 정보가 경계에서 끊기는 문제를 줄임 |

예를 들어 다음 문장이 두 청크로 잘린다고 생각해 보자.

```
청크 1: 단순 변심 반품은 수령일로부터
청크 2: 7일 이내 신청 가능합니다.
```

앞 청크만 검색되면 반품 신청 기한을 알기 어렵다. 청크 사이에 일부 내용을 겹치면 이러한 문제를 줄일 수 있다.

`RecursiveCharacterSplitter`는 일반적으로 문단 경계 → 줄바꿈 → 공백 → 문자 순서로 자연스러운 분할 지점을 찾는다.

실습에서는 `chunk_size=300`, `chunk_overlap=30`으로 시작해 볼 수 있다. 다만 정답은 없으며, 실제 크기 기준은 사용하는 분할기의 설정에 따라 달라진다.

**중요:** 청크로 나눌 때도 `source`, `category` 같은 메타데이터가 각 청크에 유지되는지 확인해야 한다.

### 청킹 품질이 중요한 이유

- 핵심 문장이 여러 청크로 잘리면 필요한 정보가 검색되지 않을 수 있다.
- 서로 다른 주제가 한 청크에 섞이면 관련성이 낮은 검색 결과가 나올 수 있다.
- 청크가 지나치게 작으면 문맥이 부족하고, 지나치게 크면 불필요한 내용이 함께 검색될 수 있다.

즉, **청킹은 단순히 글자를 자르는 작업이 아니라 검색에 적합한 정보 단위를 만드는 작업**이다.

# [ RAG 기초 ② 글자가 아니라 의미로 찾기 ]

## 4. 키워드 검색의 한계

문서를 잘게 나누었다면 이제 질문에 맞는 청크를 찾아야 한다.

가장 단순한 방법은 질문에 포함된 단어가 문서에도 있는지 확인하는 **키워드 검색**이다.

하지만 고객은 "포인트 언제 사라져요?"라고 질문하고 문서는 "적립금 유효기간"이라고 표현할 수 있다.

```
질문: 포인트 언제 사라져요?
문서: 적립금 유효기간은 1년입니다.

키워드 검색 → '포인트'가 없으면 놓칠 수 있음
의미 기반 검색 → 표현이 달라도 관련 내용을 찾을 수 있음
```

키워드 검색은 정확한 단어를 찾는 데 유용하지만, 표현이 다르거나 동의어를 사용하는 경우에는 한계가 있다.

## 5. 임베딩 — 문장의 의미를 숫자로 표현하기

**임베딩(Embedding)**은 문장이나 문서 조각을 숫자들의 묶음인 **벡터(Vector)**로 변환하는 것이다.

임베딩 모델은 문장의 의미와 맥락을 반영한 벡터를 만든다.

```
"포인트 언제 사라져요?"
          ↓
      임베딩 모델
          ↓
[0.12, -0.34, 0.81, 0.27, ...]
          ↓
     의미를 비교할 수 있는 벡터
```

질문과 문서 청크를 같은 임베딩 모델로 변환하면, 두 벡터의 유사도를 계산해 의미상 관련 있는 내용을 찾을 수 있다.

예를 들어 "포인트 소멸"과 "적립금 유효기간"은 표현은 다르지만 의미가 유사하므로 관련 결과로 검색될 수 있다.

> 임베딩은 문장을 숫자로 표현하는 것이지, 문장의 의미를 사람이 읽을 수 있는 설명으로 바꾸는 것은 아니다. 또한 의미가 비슷한 표현이라고 해서 항상 정확하게 검색되는 것은 아니다.

## 6. 벡터 DB — 임베딩을 저장하고 검색하기

문서 청크가 수천 개라면 질문이 들어올 때마다 모든 벡터를 일일이 비교하는 작업은 부담이 될 수 있다.

**벡터 데이터베이스(Vector Database)**는 벡터와 관련 정보를 저장하고, 유사한 벡터를 검색하도록 돕는다.

입문 실습에서는 **Chroma** 같은 벡터 DB를 사용할 수 있다.

### RAG의 준비 단계와 검색 단계

```
[ 준비 단계 ]

문서 파일
   ↓
Document Loader
   ↓
Document 객체
   ↓
 Splitter
   ↓
청크 + 메타데이터
   ↓
임베딩 모델
   ↓
벡터 DB에 저장


[ 질문이 들어온 뒤 ]

사용자 질문
   ↓
질문을 벡터로 변환
   ↓
벡터 DB에서 유사한 청크 검색
   ↓
관련 청크를 LLM에 전달
   ↓
문서에 근거한 답변 생성
```

문서는 보통 미리 임베딩해 저장해 두고, 질문이 들어오면 질문도 같은 임베딩 모델로 변환해 검색한다.

이렇게 하면 질문에 "포인트"라는 단어가 있어도 "적립금"을 다룬 청크를 찾을 가능성이 높아진다.

## 7. 검색 결과를 조절하는 설정

### `k` — 몇 개의 청크를 가져올까?

`k`는 검색 결과로 가져올 청크의 개수다.

| 설정 | 장점 | 주의점 |
|---|---|---|
| `k=1` | 가장 관련 있는 결과 하나만 전달 | 필요한 정보가 다른 청크에 있으면 놓칠 수 있음 |
| `k=3` | 여러 관련 내용을 함께 확인 | 일부 관련 없는 결과가 포함될 수 있음 |
| `k=5` | 더 넓은 맥락을 확보할 수 있음 | 불필요한 내용과 입력 토큰이 늘 수 있음 |

처음에는 `k=3` 또는 `k=5`로 실험하고, 검색 결과의 관련성과 답변 품질을 비교하면 좋다. 항상 정답인 값은 없다.

### `filter` — 메타데이터로 검색 범위 좁히기

청크에 저장해 둔 `category` 등의 메타데이터를 이용하면 검색 범위를 제한할 수 있다.

예를 들어 다음과 같이 환불 관련 문서만 대상으로 검색할 수 있다.

```python
filter = {"category": "refund"}
```

이렇게 하면 모든 문서를 대상으로 검색하는 대신, 조건에 맞는 문서 안에서 관련 청크를 찾을 수 있다. 단, 실제 필터 문법과 동작은 사용하는 벡터 DB와 검색 함수에 따라 확인해야 한다.

## 8. 실습에서 확인할 내용

| 실습 단계 | 확인할 것 |
|---|---|
| 문서 불러오기 | `loader.load()`로 `Document` 객체 생성 |
| 청킹 | `split_documents()`로 문서를 나누고 크기·겹침 조절 |
| 메타데이터 확인 | 각 청크에 `source`, `category`가 유지되는지 확인 |
| 임베딩·저장 | 청크를 벡터로 변환해 Chroma에 저장 |
| 의미 검색 | `similarity_search()`로 관련 청크 검색 |
| 검색 조절 | `k`와 `filter`를 바꾸며 결과 비교 |

## 9. 핵심 용어 정리

| 용어 | 의미 |
|---|---|
| Document Loader | 파일을 읽어 `Document` 객체로 변환하는 도구 |
| `page_content` | 문서 본문 |
| `metadata` | 출처·분류 등 문서의 부가 정보 |
| Chunk | 분할된 문서 조각 |
| `chunk_size` | 청크의 목표 크기 |
| `chunk_overlap` | 인접한 청크 사이에 겹치는 내용의 크기 |
| Embedding | 텍스트를 벡터로 변환하는 과정 |
| Vector | 임베딩 모델이 생성한 숫자들의 묶음 |
| Vector DB | 벡터를 저장하고 유사한 결과를 검색하는 데이터베이스 |
| Chroma | 벡터 저장·검색에 사용할 수 있는 도구 |
| `similarity_search()` | 의미상 유사한 청크를 검색하는 함수 |
| `k` | 검색할 결과 개수 |
| `filter` | 메타데이터 조건으로 검색 범위를 제한하는 방법 |

## ⭐ 최종 정리

RAG는 문서를 통째로 LLM에 전달하는 대신, **문서를 불러오고 → 청크로 나누고 → 임베딩해 저장하고 → 질문과 관련된 청크를 검색한 뒤 → LLM에 전달하는 방식**으로 동작한다.

- **청킹:** 검색하기 좋은 정보 단위를 만든다.
- **임베딩:** 텍스트를 의미 비교에 활용할 수 있는 벡터로 변환한다.
- **벡터 DB:** 벡터를 저장하고 유사한 청크를 검색한다.
- **`k`와 `filter`:** 검색 결과의 개수와 범위를 조절한다.

좋은 답변을 만들려면 LLM과 프롬프트뿐 아니라 **문서의 품질, 청킹 방식, 임베딩 모델, 검색 결과의 품질**도 함께 관리해야 한다.
