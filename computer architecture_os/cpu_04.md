# [ 04 - 1 ALU와 제어장치 ]

CPU는 크게 **ALU, 제어장치, 레지스터** 등으로 구성된다.

이번에는 그중 **ALU와 제어장치가 어떤 역할을 하는지** 알아보자.

---

## 1. ALU

**ALU(산술논리연산장치)** : CPU 내부에서 실제로 **계산과 논리 연산을 수행하는 장치**

ALU가 연산을 수행하려면 두 가지 정보가 필요하다.

> **피연산자 + 수행할 연산**

* **피연산자** → 레지스터에서 전달
* **수행할 연산** → 제어장치가 보내는 제어 신호를 통해 전달

즉,

```
레지스터 ── 피연산자 ──→ ALU
                         ↓
제어장치 ── 제어 신호 ──→ ALU
                         ↓
                       연산 수행
```

연산이 끝나면 ALU는 **연산 결과와 플래그**를 내보낸다.

* 연산 결과 → 레지스터에 저장
* 플래그 → 플래그 레지스터에 저장

### ALU의 연산 결과

연산 결과는 단순한 숫자뿐만 아니라 **문자, 주소 등 다양한 형태의 데이터**가 될 수 있다.

```
피연산자 + 연산
      ↓
     ALU
      ↓
연산 결과 → 레지스터
플래그   → 플래그 레지스터
```

---

## 2. 플래그

**플래그(flag)** : 연산 결과나 CPU의 상태를 나타내는 **부가적인 정보**

플래그는 연산 결과 자체를 저장하는 것이 아니라,

> **"연산 결과가 어떤 상태인지"를 나타내는 정보**

라고 이해하면 된다.

자주 알아야 할 플래그는 다음과 같다.

| 플래그           | 의미                            |
| ------------- | ----------------------------- |
| **부호 플래그**    | 연산 결과가 음수인지 양수인지 나타냄          |
| **제로 플래그**    | 연산 결과가 0인지 나타냄                |
| **캐리 플래그**    | 연산 결과에서 올림수나 빌림수가 발생했는지 나타냄   |
| **오버플로우 플래그** | 연산 결과가 표현할 수 있는 범위를 벗어났는지 나타냄 |

예를 들어 연산 결과가 음수라면 **부호 플래그가 설정**되고, 결과가 0이라면 **제로 플래그가 설정**된다.

> ⭐ **부호 / 제로 / 캐리 / 오버플로우 플래그 정도는 알아두자.**

---

# 3. 제어장치

**제어장치(Control Unit)** : 명령어를 해석하고, CPU의 각 구성 요소가 동작하도록 **제어 신호를 발생시키는 장치**

CPU가 명령어를 실행하려면

> "무엇을 해야 하는가?"

를 해석하고 각 부품에 신호를 보내야 한다.

이 역할을 하는 것이 제어장치다.

---

## 4. 제어장치가 받아들이는 정보

제어장치는 크게 다음과 같은 정보를 받아들인다.

| 입력 정보             | 의미                         |
| ----------------- | -------------------------- |
| **클럭**            | CPU의 동작 타이밍을 맞추는 신호        |
| **명령어 레지스터의 명령어** | 현재 실행할 명령어                 |
| **플래그 레지스터의 플래그** | 연산 결과나 CPU의 상태 정보          |
| **제어 신호**         | CPU 외부의 장치에서 전달되는 제어 관련 신호 |

### 클럭

**클럭(clock)** : 컴퓨터의 여러 부품이 일정한 박자에 맞춰 동작하도록 하는 신호

쉽게 생각하면 CPU가 움직이는 **기준 박자**라고 보면 된다.

---

### 명령어

현재 해석해야 할 명령어는 **명령어 레지스터(IR)**에 저장되어 있다.

제어장치는 명령어 레지스터에 저장된 명령어를 해석하고,

> "ALU가 계산해야 한다."
> "레지스터의 값을 이동시켜야 한다."
> "메모리에서 데이터를 가져와야 한다."

등의 동작을 수행하도록 제어 신호를 발생시킨다.

---

## 5. 제어장치가 보내는 제어 신호

제어장치는 CPU 내부와 외부로 제어 신호를 보낸다.

```
                    제어장치
                       │
          ┌────────────┴────────────┐
          ↓                         ↓
       CPU 내부                   CPU 외부
   레지스터 / ALU             메모리 / 입출력장치
```

즉, 제어장치는 **CPU 전체의 동작을 조정하는 역할**을 한다.

---

# [ 04 - 2 레지스터 ]

## 1. 레지스터란?

**레지스터(Register)** : CPU 내부에 있는 **작고 빠른 임시 저장 장치**

프로그램의 명령어와 데이터는 CPU에서 처리되는 과정에서 레지스터에 저장될 수 있다.

레지스터는 CPU 내부에 있기 때문에 일반적으로 메모리보다 빠르게 접근할 수 있다.

> ⭐ **CPU가 작업을 처리하기 위해 바로 사용할 데이터를 임시로 저장하는 공간**

CPU마다 레지스터의 종류와 개수는 다르지만, 기본적으로 다음 레지스터는 알아두자.

---

## 2. 주요 레지스터

| 레지스터                 | 역할                           |
| -------------------- | ---------------------------- |
| **프로그램 카운터(PC)**     | 다음에 실행할 명령어의 주소 저장           |
| **명령어 레지스터(IR)**     | 현재 실행할 명령어 저장                |
| **메모리 주소 레지스터(MAR)** | 읽거나 쓰려는 메모리 주소 저장            |
| **메모리 버퍼 레지스터(MBR)** | 메모리와 주고받을 데이터나 명령어 저장        |
| **플래그 레지스터**         | 연산 결과 및 CPU 상태에 대한 정보 저장     |
| **범용 레지스터**          | 다양한 상황에서 자유롭게 사용             |
| **스택 포인터(SP)**       | 스택의 꼭대기를 가리킴                 |
| **베이스 레지스터**         | 베이스 레지스터 주소 지정 방식에서 기준 주소 저장 |

---

# 3. 명령어를 가져오는 과정

CPU가 메모리에 있는 명령어를 가져와 실행하는 과정을 간단하게 살펴보자.

예를 들어 첫 번째 명령어가 **1000번지**에 있다고 하자.

### ① 프로그램 카운터

프로그램 카운터(PC)에 다음에 실행할 명령어의 주소인 **1000번지**가 저장되어 있다.

```
PC → 1000
```

### ② 메모리 주소 레지스터

CPU는 1000번지의 명령어를 가져오기 위해 해당 주소를 **메모리 주소 레지스터(MAR)**에 저장한다.

```
PC
 ↓
MAR → 1000
```

### ③ 메모리 읽기

MAR에 저장된 주소를 **주소 버스**를 통해 메모리에 전달하고,

CPU는 메모리에 **읽기 제어 신호**를 보낸다.

```
CPU ── 주소(1000) ──→ 메모리
CPU ── 읽기 신호 ───→ 메모리
```

### ④ 메모리 버퍼 레지스터

메모리는 1000번지에 저장된 값을 데이터 버스를 통해 CPU로 전달한다.

예를 들어 1000번지에 `1101`이라는 명령어가 저장되어 있다면,

```
메모리
  │
  │ 1101
  ↓
데이터 버스
  │
  ↓
MBR → 1101
```

이때 프로그램 카운터는 **다음 명령어의 주소를 가리키도록 증가**한다.

> 일반적인 순차 실행에서는 다음 명령어가 바로 뒤에 있기 때문에 PC가 증가한다.

### ⑤ 명령어 레지스터

메모리 버퍼 레지스터에 가져온 `1101` 명령어를 **명령어 레지스터(IR)**로 이동시킨다.

```
MBR → IR
1101 → 1101
```

이제 제어장치는 명령어 레지스터의 명령어를 해석하여 CPU가 어떤 작업을 해야 하는지 결정한다.

---

## 4. 전체 흐름

앞의 내용을 하나로 연결하면 다음과 같다.

```
프로그램 카운터
      ↓
메모리 주소 레지스터
      ↓
   주소 버스
      ↓
     메모리
      ↓
   데이터 버스
      ↓
메모리 버퍼 레지스터
      ↓
명령어 레지스터
      ↓
    제어장치
      ↓
명령어 해석 및 제어 신호 발생
```

이 흐름이 **명령어를 인출하는 기본적인 과정**이다.

---

# 5. 프로그램 카운터의 흐름이 바뀌는 경우

프로그램 카운터는 일반적으로 다음 명령어를 순서대로 가리키며 증가한다.

하지만 항상 순서대로 실행되는 것은 아니다.

대표적으로 다음과 같은 경우 실행 흐름이 바뀐다.

| 상황            | 설명                        |
| ------------- | ------------------------- |
| **분기/점프 명령어** | 특정 메모리 주소로 실행 흐름을 이동      |
| **인터럽트 발생**   | 현재 실행 흐름을 잠시 중단하고 인터럽트 처리 |
| **조건부 분기**    | 특정 플래그나 조건에 따라 다른 위치로 이동  |

따라서 PC는 단순히 `+1`만 하는 레지스터가 아니라,

> **다음에 실행할 명령어의 위치를 가리키는 레지스터**

라고 이해하는 것이 중요하다.

---

# 6. 스택 포인터

**스택 포인터(SP)** : 스택의 꼭대기(top)를 가리키는 레지스터

스택은 메모리의 특정 영역에 위치하며, **LIFO(후입선출)** 방식으로 데이터를 관리한다.

```
      스택
┌──────────┐
│          │
├──────────┤
│ 데이터   │ ← 스택의 꼭대기
└──────────┘
      ↑
     SP
```

스택 포인터는 현재 스택의 꼭대기가 어디인지 나타낸다.

> ⭐ 스택과 스택 포인터는 이후 함수 호출, 복귀 주소 저장 등에서도 중요하게 사용된다.

---

# 7. 베이스 레지스터와 변위 주소 지정

베이스 레지스터는 **변위 주소 지정 방식**에서 사용된다.

**변위 주소 지정 방식**은

> **기준이 되는 주소 + 변위 값**

을 계산하여 실제 데이터가 있는 **유효 주소**를 구하는 방식이다.

---

## 상대 주소 지정

프로그램 카운터(PC)를 기준으로 한다.

```
유효 주소 = PC + 변위 값
```

예를 들어,

```
PC = 100
변위 = +50

→ 유효 주소 = 150
```

즉, 현재 위치에서 **얼마나 떨어져 있는가**를 이용해 주소를 계산한다.

---

## 베이스 레지스터 주소 지정

베이스 레지스터를 기준으로 한다.

```
유효 주소 = 베이스 레지스터 + 변위 값
```

예를 들어,

```
베이스 레지스터 = 200
변위 = +50

→ 유효 주소 = 250
```

즉, **베이스 레지스터가 기준점이 되고 변위 값만큼 떨어진 위치**를 찾는 방식이다.

---

## 두 방식 비교

| 방식                 | 기준           | 유효 주소         |
| ------------------ | ------------ | ------------- |
| **상대 주소 지정**       | 프로그램 카운터(PC) | PC + 변위       |
| **베이스 레지스터 주소 지정** | 베이스 레지스터     | 베이스 레지스터 + 변위 |

> ⭐ 핵심은 둘 다 **기준 주소 + 변위 = 유효 주소**라는 것이다.

---

# [ 04 - 3 명령어 사이클과 인터럽트 ]

## 1. 명령어 사이클

CPU는 프로그램의 명령어를 아무렇게나 실행하는 것이 아니라 일정한 순서와 주기에 따라 처리한다.

이러한 **명령어의 실행 흐름과 주기**를 **명령어 사이클**이라고 한다.

가장 기본적인 흐름은 다음과 같다.

```
인출 → 실행 → 인출 → 실행 → ...
```

### 인출 사이클

**인출(Fetch)** : 메모리에서 CPU로 명령어를 가져오는 과정

```
메모리 → CPU
```

### 실행 사이클

**실행(Execute)** : 가져온 명령어를 해석하고 실제로 수행하는 과정

```
명령어 해석 → 필요한 동작 수행
```

따라서 CPU는 일반적으로

> **인출 → 실행 → 인출 → 실행**

을 반복한다.

---

# 2. 간접 사이클

모든 명령어가 인출 후 바로 실행되는 것은 아니다.

앞에서 배운 **간접 주소 지정 방식**처럼 한 번 더 메모리에 접근하여 실제 유효 주소를 알아내야 하는 경우가 있다.

이때는

```
인출 → 간접 → 실행
```

순서로 진행될 수 있다.

**간접 사이클** : 간접 주소 지정 방식 등에서 실제 데이터를 찾기 위해 추가로 메모리에 접근하는 과정

---

# 3. 인터럽트

CPU는 기본적으로

```
인출 → 실행 → 인출 → 실행
```

이라는 흐름으로 동작한다.

그런데 이 흐름을 **잠시 중단하고 다른 작업을 처리해야 하는 상황**이 발생할 수 있다.

이것을 **인터럽트(Interrupt)**라고 한다.

> ⭐ 인터럽트 = CPU가 정상적으로 실행하던 흐름을 잠시 중단하고 다른 작업을 처리하는 것

---

# 4. 인터럽트의 종류

크게 **동기 인터럽트와 비동기 인터럽트**로 나눌 수 있다.

| 종류           | 다른 이름         | 발생 원인                   |
| ------------ | ------------- | ----------------------- |
| **동기 인터럽트**  | 예외(Exception) | CPU가 명령어를 실행하는 과정에서 발생  |
| **비동기 인터럽트** | 하드웨어 인터럽트     | 주로 입출력 장치 등의 외부 요인으로 발생 |

---

## 동기 인터럽트

CPU가 명령어를 실행하는 과정에서 발생하는 인터럽트다.

예를 들어 프로그램 실행 중 예외적인 상황이 발생하면 CPU의 정상적인 흐름이 중단될 수 있다.

> **명령어 실행과 관련하여 발생하는 인터럽트**

---

## 비동기 인터럽트

**하드웨어 인터럽트**라고도 한다.

주로 입출력 장치에 의해 발생한다.

예를 들어,

* 키보드 입력
* 마우스 입력
* 프린터 작업 완료
* 저장 장치의 작업 완료

등이 있다.

---

# 5. 하드웨어 인터럽트가 필요한 이유

입출력 장치는 일반적으로 CPU보다 동작 속도가 느리다.

예를 들어 CPU가 프린터에 출력 작업을 요청했다고 하자.

인터럽트가 없다면 CPU는 계속해서

```
"완료됐나?"
"완료됐나?"
"완료됐나?"
```

라고 확인해야 한다.

이런 방식은 CPU의 시간을 낭비하게 만든다.

반면 인터럽트를 사용하면,

```
CPU → 프린터 : 출력해줘
CPU → 다른 작업 수행

프린터 → CPU : 출력 완료!
              ↑
          인터럽트 요청
```

CPU가 다른 작업을 수행하다가 **입출력 장치의 작업이 끝났다는 신호를 받으면 처리**할 수 있다.

> ⭐ 인터럽트의 중요한 목적 중 하나는 **CPU가 느린 입출력 장치를 기다리며 시간을 낭비하지 않도록 하는 것**이다.

---

# 6. 하드웨어 인터럽트 처리 과정

하드웨어 인터럽트가 발생하면 대략 다음 순서로 처리된다.

### ① 인터럽트 요청

입출력 장치가 CPU에 **인터럽트 요청 신호**를 보낸다.

```
입출력 장치 → CPU
        "처리할 일이 있습니다."
```

### ② CPU가 인터럽트 확인

CPU는 현재 명령어의 실행을 마친 뒤 인터럽트 요청이 있는지 확인한다.

### ③ 인터럽트 수용 가능 여부 확인

CPU는 **인터럽트 플래그**를 확인하여 현재 인터럽트를 받아들일 수 있는지 확인한다.

### ④ 현재 작업 백업

인터럽트를 처리하기 전에 현재 실행 중이던 작업을 나중에 다시 이어서 실행할 수 있도록 필요한 상태를 저장한다.

```
현재 작업 상태
     ↓
    백업
```

### ⑤ 인터럽트 서비스 루틴 실행

CPU는 **인터럽트 벡터**를 참조하여 해당 인터럽트를 처리하기 위한 **인터럽트 서비스 루틴(ISR)**을 찾아 실행한다.

### ⑥ 원래 작업 복구

인터럽트 서비스 루틴 실행이 끝나면 이전에 백업해 두었던 CPU 상태를 복구하고 원래 실행하던 프로그램으로 돌아간다.

전체 흐름은 다음과 같다.

```
인터럽트 요청
     ↓
CPU가 인터럽트 확인
     ↓
인터럽트 수용 가능 여부 확인
     ↓
현재 작업 백업
     ↓
인터럽트 벡터 참조
     ↓
인터럽트 서비스 루틴 실행
     ↓
백업한 작업 복구
     ↓
원래 작업 계속 실행
```

---

# 7. 인터럽트 플래그

**인터럽트 플래그** : CPU가 **인터럽트를 받아들일 수 있는 상태인지**를 나타내는 플래그

인터럽트 플래그가 비활성화되어 있으면 일반적인 **마스크 가능한 인터럽트**를 받아들이지 않을 수 있다.

하지만 모든 인터럽트를 막을 수 있는 것은 아니다.

정전이나 하드웨어 고장처럼 **매우 긴급한 상황**을 처리하기 위한 인터럽트는 일반적인 인터럽트 플래그로 막을 수 없으며, 이를 **NMI(Non-Maskable Interrupt, 비마스크 가능 인터럽트)**라고 한다.

> ⭐ **일반적인 인터럽트는 필요에 따라 막을 수 있지만, 긴급한 인터럽트는 막을 수 없다.**

---

# 8. 인터럽트 서비스 루틴(ISR)

**인터럽트 서비스 루틴(Interrupt Service Routine)** : 특정 인터럽트가 발생했을 때 그 인터럽트를 처리하기 위해 실행되는 프로그램

예를 들어,

```
키보드 인터럽트 발생
      ↓
키보드 인터럽트 서비스 루틴 실행
      ↓
키보드 입력 처리
```

마찬가지로 다른 장치에서 인터럽트가 발생하면 해당 장치와 상황에 맞는 인터럽트 서비스 루틴이 실행된다.

인터럽트 서비스 루틴 역시 **프로그램이므로 메모리에 저장**되어 있다.

---

# 9. 인터럽트 벡터

그렇다면 CPU는 수많은 인터럽트 서비스 루틴 중에서 **어떤 루틴을 실행해야 하는지** 어떻게 알까?

이때 사용하는 것이 **인터럽트 벡터**다.

**인터럽트 벡터(Interrupt Vector)** : 각 인터럽트 서비스 루틴의 시작 위치를 알 수 있도록 해주는 정보

쉽게 말하면,

> **"이 인터럽트가 발생하면 이 위치에 있는 인터럽트 서비스 루틴을 실행해!"**

라고 알려주는 정보다.

```
인터럽트 발생
     ↓
인터럽트 벡터 확인
     ↓
해당 ISR의 시작 주소 확인
     ↓
인터럽트 서비스 루틴 실행
```

---

# 10. 인터럽트가 발생하면 기존 작업은 어떻게 될까?

예를 들어 CPU가 현재 **1500번지의 프로그램**을 실행하고 있다고 하자.

그런데 인터럽트가 발생하여 **10번지에 있는 인터럽트 서비스 루틴**을 실행해야 한다면,

CPU는 실행 위치를 인터럽트 서비스 루틴의 시작 위치로 변경해야 한다.

하지만 기존 작업을 그냥 버리면 인터럽트 처리가 끝난 뒤 원래 프로그램으로 돌아갈 수 없다.

따라서 CPU는 **현재 작업을 백업한 후 인터럽트 서비스 루틴을 실행**한다.

개념적으로는 다음과 같다.

```
기존 프로그램 실행
      ↓
현재 CPU 상태 백업
      ↓
인터럽트 서비스 루틴 실행
      ↓
백업한 CPU 상태 복구
      ↓
기존 프로그램으로 돌아감
```

이때 백업에는 **프로그램 카운터를 비롯해 인터럽트 처리 후 기존 작업을 이어가기 위해 필요한 CPU 상태 정보**가 포함된다.

> ⭐ 핵심은 **"기존 작업을 저장해 두고 → 인터럽트를 처리하고 → 기존 작업을 복구한다"**는 것이다.

# 04장 전체 흐름

이번 장의 내용을 하나의 흐름으로 연결하면 다음과 같다.

```
                CPU
                 │
       ┌─────────┼─────────┐
       ↓         ↓         ↓
      ALU      제어장치    레지스터
       │         │         │
       │         │         ├─ PC
       │         │         ├─ IR
       │         │         ├─ MAR
       │         │         ├─ MBR
       │         │         ├─ 플래그 레지스터
       │         │         ├─ 범용 레지스터
       │         │         ├─ SP
       │         │         └─ 베이스 레지스터
       │         │
       └───── 명령어 실행 ─────┘
                 │
                 ↓
        인출 → 실행 → 인출 → 실행
                 │
                 ↓
             인터럽트 발생
                 │
                 ↓
          현재 작업 백업
                 │
                 ↓
       인터럽트 서비스 루틴
                 │
                 ↓
           기존 작업 복구
```

# ⭐ 04장 핵심 정리

### ALU

> **실제로 계산하고 논리 연산을 수행하는 장치**

### 제어장치

> **명령어를 해석하고 CPU의 각 장치에 제어 신호를 보내는 장치**

### 레지스터

> **CPU 내부에서 명령어와 데이터를 임시로 저장하는 빠른 저장 공간**

### 주요 레지스터

> **PC = 다음 명령어 주소 / IR = 현재 명령어 / MAR = 메모리 주소 / MBR = 메모리와 주고받는 값**

### 플래그 레지스터

> **연산 결과나 CPU 상태에 대한 부가 정보 저장**

### 명령어 사이클

> **인출 → 실행을 반복하며 명령어를 처리하는 과정**

### 인터럽트

> **CPU가 기존 실행 흐름을 잠시 중단하고 다른 작업을 처리하는 것**

### 인터럽트 처리

> **인터럽트 요청 → 현재 작업 백업 → ISR 실행 → 기존 작업 복구**

### 인터럽트 벡터

> **실행해야 할 인터럽트 서비스 루틴의 위치를 알려주는 정보**

## 🔗 앞에서 배운 내용과 연결

03장에서 배운 **명령어**가 실제 CPU에서 실행되는 과정을 이번 장에서 살펴본 것이다.

```
03장
명령어
  ↓
opcode + operand
  ↓
주소 지정 방식
  ↓
────────────────────
04장
  ↓
명령어를 메모리에서 인출
  ↓
레지스터에 저장
  ↓
제어장치가 명령어 해석
  ↓
ALU가 연산 수행
  ↓
결과와 플래그 저장
  ↓
다음 명령어 인출
  ↓
반복
```

즉,

> **03장에서는 "명령어가 무엇인지"를 배웠다면, 04장에서는 "그 명령어가 CPU에서 어떻게 실행되는지"를 배우는 것이다.**
