# [ 08 - 1 입출력장치 - 장치 컨트롤러와 드라이버 ]

> ※ 입출력장치에는 키보드, 마우스뿐만 아니라 **보조기억장치(HDD, SSD 등)**도 포함된다.

컴퓨터 내부의 CPU와 메모리는 서로 정해진 방식으로 데이터를 주고받지만, 입출력장치는 종류와 특성이 매우 다양하다.

그렇다면 입출력장치는 컴퓨터 내부와 어떻게 데이터를 주고받을까?

---

## 1. 입출력장치를 직접 연결하기 어려운 이유

입출력장치를 CPU나 메모리에 직접 연결하여 사용하기 어려운 이유는 크게 두 가지를 먼저 이해하면 된다.

### ① 입출력장치의 종류가 매우 다양하다

키보드, 마우스, 프린터, 모니터, 저장장치 등 장치마다

* 데이터 전송 방식
* 속도
* 규격
* 통신 방식

등이 서로 다르다.

따라서 CPU가 모든 입출력장치를 직접 제어하도록 만들면 매우 복잡해진다.

### ② CPU·메모리와 입출력장치의 속도 차이가 크다

CPU와 메모리는 매우 빠르게 동작하지만 키보드, 마우스, 프린터 등의 입출력장치는 상대적으로 느리다.

예를 들어 CPU가 프린터의 작업이 끝날 때까지 직접 기다린다면 CPU의 처리 능력을 제대로 활용하지 못하게 된다.

> ⭐ **입출력장치는 종류도 다양하고 속도도 제각각이기 때문에 CPU가 직접 처리하기 어렵다.**

그래서 CPU와 입출력장치 사이에 **장치 컨트롤러**를 둔다.

```
CPU / 메모리
     ↕
  시스템 버스
     ↕
장치 컨트롤러
     ↕
입출력장치
```

---

# 2. 장치 컨트롤러

**장치 컨트롤러(Device Controller)**
: 입출력장치를 컴퓨터 시스템과 연결하여 **입출력 작업을 제어하고 CPU와 장치 사이의 데이터 교환을 담당하는 하드웨어**

쉽게 말하면,

> **CPU와 입출력장치 사이의 통역자이자 중간 관리자**

라고 생각하면 된다.

### 주요 역할

| 역할          | 설명                                    |
| ----------- | ------------------------------------- |
| **통신 중계**   | CPU와 입출력장치 사이에서 명령과 데이터를 주고받음         |
| **상태 확인**   | 장치가 준비되었는지, 작업이 끝났는지, 오류가 있는지 확인      |
| **데이터 버퍼링** | 속도가 다른 장치 사이에서 데이터를 임시 저장하여 속도 차이를 완화 |
| **오류 관리**   | 입출력 과정에서 발생한 오류를 확인하고 처리              |

---

# 3. 장치 컨트롤러의 주요 레지스터

장치 컨트롤러에는 CPU와 입출력장치가 정보를 주고받기 위한 여러 레지스터가 존재한다.

대표적으로 다음 세 가지를 이해하면 된다.

| 레지스터         | 역할                      |
| ------------ | ----------------------- |
| **상태 레지스터**  | 장치의 현재 상태 저장            |
| **제어 레지스터**  | CPU가 장치에 내리는 명령이나 설정 저장 |
| **데이터 레지스터** | 실제로 주고받는 데이터 저장         |

### 상태 레지스터

**Status Register**

입출력장치의 현재 상태를 저장한다.

예를 들어,

```
준비 완료
작업 중
오류 발생
```

등의 상태를 확인할 수 있다.

### 제어 레지스터

**Control Register**

CPU가 입출력장치에 어떤 작업을 수행할지 설정하는 데 사용된다.

예를 들어,

```
읽기
쓰기
장치 시작
장치 정지
```

등의 제어 정보가 들어갈 수 있다.

### 데이터 레지스터

**Data Register**

CPU와 입출력장치 사이에서 실제로 주고받는 데이터를 저장한다.

```
CPU
 ↕
데이터 레지스터
 ↕
입출력장치
```

데이터를 잠시 저장하는 **버퍼 역할**도 할 수 있다.

---

# 4. 장치 드라이버

장치 컨트롤러가 **하드웨어**라면 장치 드라이버는 그 하드웨어를 사용하기 위한 **소프트웨어**다.

**장치 드라이버(Device Driver)**
: 운영체제가 특정 입출력장치를 사용할 수 있도록 **장치 컨트롤러를 제어하는 소프트웨어**

쉽게 생각하면,

> **장치 컨트롤러 = 하드웨어**
> **장치 드라이버 = 그 하드웨어를 사용하기 위한 소프트웨어**

라고 이해하면 된다.

전체적인 관계는 다음과 같다.

```
사용자 프로그램
      ↓
운영체제
      ↓
장치 드라이버
      ↓
장치 컨트롤러
      ↓
입출력장치
```

따라서 새로운 입출력장치를 컴퓨터에서 사용하려면 운영체제가 해당 장치를 제어할 수 있도록 **적절한 드라이버가 필요하다.**

> ⭐ 장치 드라이버는 **운영체제와 하드웨어 사이를 연결하는 소프트웨어**라고 이해하자.

---

# [ 08 - 2 다양한 입출력 방법 ]

CPU와 장치 컨트롤러는 어떤 방식으로 데이터를 주고받을까?

대표적인 입출력 방식은 크게 세 가지다.

> **프로그램 입출력 → 인터럽트 기반 입출력 → DMA 입출력**

---

# 1. 프로그램 입출력(PIO)

**프로그램 입출력(Programmed I/O)**
: CPU가 프로그램의 명령어를 통해 **장치 컨트롤러의 상태와 데이터를 직접 확인하고 입출력을 수행하는 방식**

쉽게 말하면,

> **CPU가 입출력장치를 계속 확인하면서 직접 작업하는 방식**

이다.

---

## 프로그램 입출력 예시

메모리에 있는 데이터를 하드 디스크에 저장한다고 생각해보자.

### ① CPU가 쓰기 명령 전달

CPU가 하드 디스크 컨트롤러의 **제어 레지스터**에 쓰기 작업을 요청한다.

### ② 장치 상태 확인

하드 디스크 컨트롤러는 현재 장치의 상태를 확인하고 **상태 레지스터**에 상태를 표시한다.

### ③ CPU가 계속 확인

CPU는 상태 레지스터를 주기적으로 확인한다.

```
CPU
 ↓
"준비됐나?"
 ↓
상태 레지스터 확인
 ↓
아직 준비 안 됨
 ↓
다시 확인
```

이처럼 CPU가 장치의 상태를 계속 확인하는 것을 **폴링(Polling)**이라고 한다.

### ④ 데이터 전달

장치가 준비되면 CPU가 메모리의 데이터를 **데이터 레지스터**에 기록한다.

### ⑤ 작업 완료 확인

CPU는 작업이 끝났는지 다시 확인하고, 완료되면 입출력 작업을 종료한다.

전체 흐름은 다음과 같다.

```
CPU
 ↓
제어 레지스터에 명령
 ↓
장치 컨트롤러
 ↓
상태 레지스터 확인
 ↓
[준비 안 됨] → 계속 확인
 ↓
[준비 완료]
 ↓
데이터 레지스터에 데이터 전달
 ↓
입출력 완료
```

> ⭐ 프로그램 입출력의 핵심은 **CPU가 직접 상태를 확인하고 입출력을 제어한다는 것**이다.

---

# 2. 메모리 맵 입출력과 고립형 입출력

CPU가 메모리와 입출력장치의 레지스터를 구분하여 접근하는 방법에는 대표적으로 두 가지가 있다.

## 메모리 맵 입출력(Memory-Mapped I/O)

**메모리 주소 공간과 입출력장치의 레지스터 주소 공간을 하나의 주소 공간으로 관리하는 방식**

즉, 입출력장치의 레지스터도 메모리 주소처럼 취급한다.

```
하나의 주소 공간
┌─────────────────┐
│      메모리      │
├─────────────────┤
│ 입출력장치 레지스터 │
└─────────────────┘
```

따라서 일반적인 **메모리 읽기/쓰기 명령어**를 사용하여 입출력장치의 레지스터에도 접근할 수 있다.

---

## 고립형 입출력(Isolated I/O)

**메모리 주소 공간과 입출력장치의 주소 공간을 별도로 분리하여 관리하는 방식**

```
메모리 주소 공간     입출력 주소 공간
┌──────────────┐    ┌──────────────┐
│    메모리     │    │ 입출력장치    │
└──────────────┘    │ 레지스터      │
                    └──────────────┘
```

입출력장치에 접근할 때는 **입출력 전용 명령어**를 사용한다.

예:

```
IN
OUT
```

---

## 두 방식 비교

| 구분      | 메모리 맵 입출력         | 고립형 입출력      |
| ------- | ----------------- | ------------ |
| 주소 공간   | 메모리와 입출력장치가 통합    | 별도로 분리       |
| 접근 방법   | 일반 메모리 읽기/쓰기      | 전용 입출력 명령어   |
| 대표적인 개념 | 메모리 주소 공간에 I/O 포함 | I/O 전용 주소 공간 |

> ⭐ 핵심은 **"입출력장치의 레지스터를 메모리처럼 취급할 것인가, 별도의 주소 공간으로 취급할 것인가"**이다.

---

# 3. 인터럽트 기반 입출력

프로그램 입출력에서는 CPU가 장치의 상태를 계속 확인해야 했다.

하지만 이것은 CPU의 시간을 낭비한다.

이를 해결하는 방법이 **인터럽트 기반 입출력**이다.

**인터럽트 기반 입출력(Interrupt-Driven I/O)**
: CPU가 장치의 상태를 계속 확인하지 않고, **장치 컨트롤러가 작업을 완료하면 CPU에 인터럽트를 요청하는 방식**

```
CPU → 입출력장치 : 작업 요청

CPU → 다른 작업 수행

입출력장치 → CPU : 작업 완료!
                   ↓
              인터럽트 요청
```

따라서 CPU는 입출력장치가 작업을 끝낼 때까지 계속 기다릴 필요가 없다.

> ⭐ **프로그램 입출력 = CPU가 계속 확인**
> ⭐ **인터럽트 기반 입출력 = 장치가 끝나면 CPU에게 알려줌**

---

# 4. NMI와 Maskable Interrupt

인터럽트는 크게 다음과 같이 구분할 수 있다.

| 종류                     | 설명                                      |
| ---------------------- | --------------------------------------- |
| **Maskable Interrupt** | 필요에 따라 인터럽트 플래그 등을 통해 수용하지 않을 수 있는 인터럽트 |
| **NMI**                | 일반적인 방법으로 막을 수 없는 인터럽트                  |

### Maskable Interrupt

일반적인 하드웨어 인터럽트는 CPU의 **인터럽트 플래그**에 따라 받아들이지 않을 수 있다.

### NMI

**NMI(Non-Maskable Interrupt)**는 일반적인 방법으로 막을 수 없는 인터럽트다.

예를 들어 심각한 하드웨어 오류나 전원 이상과 같이 즉시 처리해야 하는 상황에 사용될 수 있다.

> ⭐ **NMI = 매우 긴급하여 일반적인 방법으로 무시할 수 없는 인터럽트**

---

# 5. PIC

입출력장치가 하나뿐이라면 인터럽트 처리가 비교적 단순하다.

하지만 실제 컴퓨터에는 키보드, 마우스, 저장장치 등 여러 장치가 존재한다.

여러 장치에서 동시에 인터럽트 요청이 발생한다면 CPU는 어떤 요청을 먼저 처리해야 할까?

이때 사용되는 것이 **PIC**이다.

**PIC(Programmable Interrupt Controller)**
: 여러 장치에서 발생하는 인터럽트 요청을 받아 **우선순위를 판단하고 CPU에 전달하는 장치**

```
키보드 ──┐
마우스 ──┤
저장장치 ─┤
          ↓
         PIC
          ↓
       CPU
```

즉,

> **여러 인터럽트 요청을 관리하여 CPU에 전달하는 하드웨어**

라고 이해하면 된다.

---

# 6. DMA 입출력

프로그램 입출력이나 인터럽트 기반 입출력에서는 CPU가 입출력 과정에 계속 관여한다.

특히 대량의 데이터를 이동할 때 CPU가 데이터를 직접 옮기게 되면 CPU의 작업 부담이 커진다.

이 문제를 해결하기 위한 방법이 **DMA**다.

**DMA(Direct Memory Access)**
: CPU의 개입을 줄이고 **DMA 컨트롤러가 메모리에 직접 접근하여 입출력장치와 메모리 사이의 데이터를 전송하는 방식**

> 여기서 중요한 것은 **CPU가 완전히 입출력에서 빠지는 것이 아니라, 데이터 이동 작업을 CPU 대신 DMA 컨트롤러가 담당한다는 것**이다.

---

# 7. DMA가 필요한 이유

기존 방식에서는 데이터가 이동할 때 CPU가 중간에서 관여할 수 있다.

```
입출력장치
    ↓
장치 컨트롤러
    ↓
CPU
    ↓
메모리
```

대량의 데이터를 이렇게 옮기면 CPU가 데이터 전송에 많은 시간을 사용하게 된다.

DMA를 사용하면,

```
입출력장치
    ↓
장치 컨트롤러
    ↓
DMA 컨트롤러
    ↓
메모리
```

처럼 **DMA 컨트롤러가 데이터 이동을 담당**할 수 있다.

CPU는 데이터 하나하나를 옮기는 대신 DMA 컨트롤러에게

> "어디에서 어디로, 얼마나 옮겨라."

라는 정보를 설정해주고 다른 작업을 수행할 수 있다.

---

# 8. DMA 동작 과정

### ① CPU가 DMA 컨트롤러 설정

CPU가 DMA 컨트롤러에 필요한 정보를 전달한다.

예:

```
입출력장치 주소
메모리 주소
전송할 데이터 크기
```

### ② DMA 컨트롤러가 데이터 전송

DMA 컨트롤러가 장치 컨트롤러와 메모리 사이의 데이터 이동을 수행한다.

### ③ 데이터 전송 완료

전송이 끝나면 DMA 컨트롤러가 CPU에 **인터럽트**를 발생시켜 완료 사실을 알린다.

전체 흐름은 다음과 같다.

```
CPU
 ↓
DMA 컨트롤러 설정
 ↓
CPU는 다른 작업 수행
 ↓
DMA 컨트롤러가 데이터 전송
 ↓
전송 완료
 ↓
DMA → CPU : 인터럽트
```

> ⭐ **DMA의 핵심 = CPU가 데이터 이동을 직접 처리하지 않고 DMA 컨트롤러가 대신 처리**

---

# 9. 사이클 스틸링

DMA 컨트롤러가 메모리에 접근하려면 **버스**를 사용해야 한다.

CPU 역시 메모리에 접근하기 위해 버스를 사용한다.

따라서 DMA가 버스를 사용하면 CPU가 잠시 버스를 사용하지 못할 수 있다.

이것을 **사이클 스틸링(Cycle Stealing)**이라고 한다.

> DMA가 CPU의 버스 사용 기회를 일부 가져가는 것처럼 보이기 때문에 붙은 이름이다.

```
CPU : 버스 사용
CPU : 버스 사용
DMA : 버스 사용
CPU : 버스 사용
DMA : 버스 사용
```

DMA가 CPU의 버스 사용 주기를 일부 가져가는 것이다.

---

# 10. 입출력 버스

DMA와 같은 입출력 작업이 많아지면 CPU와 메모리가 사용하는 시스템 버스의 부담이 커질 수 있다.

그래서 시스템에서는 입출력 장치들을 위한 별도의 **입출력 버스(I/O Bus)**를 사용하기도 한다.

대표적인 예로

> **PCI, PCIe**

등이 있다.

입출력 버스를 사용하면 입출력 장치와 CPU·메모리 사이의 데이터 이동을 효율적으로 처리할 수 있다.

```
          CPU
           │
         시스템 버스
           │
         메모리
           
           │
      입출력 버스
           │
   ┌───────┼───────┐
   ↓       ↓       ↓
 장치     장치     장치
컨트롤러 컨트롤러 컨트롤러
```

> ⭐ **DMA = 데이터 이동을 CPU 대신 담당하는 방식**
> ⭐ **입출력 버스 = 입출력 장치의 데이터 전송을 위한 경로**

---

# [ 08 - 3 레지스터 직접 조작해 입출력해보기 ]

앞에서 장치 컨트롤러와 레지스터, 인터럽트 등을 이론적으로 배웠다.

그렇다면 실제 프로그램에서는 이러한 하드웨어를 어떻게 제어할까?

---

# 1. 레지스터 직접 제어

저수준 프로그래밍 환경에서는 특정 주소에 값을 직접 읽거나 쓰는 방식으로 하드웨어 레지스터를 제어할 수 있다.

예를 들어,

```
특정 주소
   ↓
레지스터
   ↓
비트 값을 설정
   ↓
입출력장치 동작 변경
```

C언어와 같은 저수준 프로그래밍 환경에서는 특정 메모리 주소나 I/O 포트에 값을 기록하여 하드웨어의 동작을 설정할 수 있다.

특히 **비트 연산**을 이용하여 레지스터의 특정 비트를 켜거나 끄는 방식이 많이 사용된다.

예를 들어 레지스터의 비트가

```
0000
```

이었다가 특정 비트를 설정하면

```
1111
```

처럼 상태를 변경할 수 있다.

---

# 2. 입출력 방향 설정

하드웨어에서는 레지스터의 비트를 이용하여 장치의 동작을 설정할 수 있다.

예를 들어 GPIO와 같은 장치에서는 특정 핀을

```
입력(Input)
출력(Output)
```

중 어떤 방식으로 사용할지 설정할 수 있다.

이처럼 **레지스터에 값을 기록하는 것만으로도 하드웨어의 동작 방식을 변경**할 수 있다.

---

# 3. 인터럽트와 ISR

하드웨어 인터럽트가 발생하면 CPU는 해당 인터럽트를 처리하기 위한 **인터럽트 서비스 루틴(ISR)**을 실행한다.

예를 들어 스위치를 누르는 상황을 생각해보자.

```
스위치 입력
    ↓
하드웨어 인터럽트 발생
    ↓
CPU가 인터럽트 수용
    ↓
ISR 실행
    ↓
레지스터 값 변경
    ↓
LED 상태 변경
```

예를 들어 스위치를 누르면

```
0000 → 1111
```

처럼 출력 레지스터의 값을 변경하여 LED의 상태를 바꿀 수 있다.

---

# 4. 실제 시스템에서의 위치

레지스터를 직접 조작하는 방식은 일반적인 애플리케이션 프로그래밍보다는 **운영체제, 장치 드라이버, 펌웨어 등 하드웨어에 가까운 소프트웨어 계층**에서 중요하게 사용된다.

전체적인 관계를 연결하면 다음과 같다.

```
사용자 프로그램
      ↓
운영체제
      ↓
장치 드라이버
      ↓
장치 컨트롤러의 레지스터
      ↓
입출력장치
```

하드웨어에 가까워질수록 특정 레지스터의 값을 직접 읽고 쓰거나 비트 연산을 이용하여 장치를 제어하는 작업이 많아진다.

---

# ⭐ 08장 전체 흐름

08장의 내용을 하나의 흐름으로 연결하면 다음과 같다.

```
입출력장치는 종류가 다양하고 속도도 다름
                ↓
CPU가 직접 처리하기 어려움
                ↓
        장치 컨트롤러
                ↓
CPU와 입출력장치 사이의 통신 담당
                ↓
      상태 / 제어 / 데이터 레지스터
                ↓
       장치 드라이버가 제어
                ↓
        입출력 방식 선택
                ↓
 ┌──────────┬────────────┬──────────┐
 ↓          ↓            ↓
PIO       인터럽트       DMA
 ↓          ↓            ↓
CPU가     장치가       DMA가
계속 확인  완료 후       데이터 이동
           CPU에 알림
                ↓
        입출력 작업 완료
```

---

# ⭐ 08장 핵심 정리

### 장치 컨트롤러

> **CPU와 입출력장치 사이에서 통신과 제어를 담당하는 하드웨어**

### 장치 컨트롤러의 주요 레지스터

> **상태 레지스터 = 현재 상태**
> **제어 레지스터 = 제어 명령**
> **데이터 레지스터 = 실제 데이터**

### 장치 드라이버

> **운영체제가 특정 입출력장치를 사용할 수 있도록 장치 컨트롤러를 제어하는 소프트웨어**

### 프로그램 입출력

> **CPU가 장치의 상태를 직접 확인하면서 입출력을 수행**

### 인터럽트 기반 입출력

> **장치가 작업을 완료하면 CPU에 인터럽트를 보내도록 하는 방식**

### DMA

> **DMA 컨트롤러가 CPU의 개입을 줄이고 메모리와 입출력장치 사이의 데이터를 직접 이동시키는 방식**

### PIC

> **여러 장치의 인터럽트 요청을 관리하고 우선순위를 판단하여 CPU에 전달**

### NMI

> **일반적인 방법으로 막을 수 없는 긴급한 인터럽트**

### 메모리 맵 입출력

> **메모리와 입출력장치의 주소 공간을 하나로 관리**

### 고립형 입출력

> **메모리와 입출력장치의 주소 공간을 분리하고 별도의 입출력 명령어 사용**
