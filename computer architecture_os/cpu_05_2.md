# 05-2. 명령어 병렬 처리 기법

## 📌 학습 목표

* 명령어 파이프라인이 무엇인지 이해하기
* 파이프라인 위험의 종류와 원인 이해하기
* 슈퍼스칼라가 무엇인지 이해하기
* 비순차적 명령어 처리가 무엇인지 이해하기

---

# 1. CPU가 시간을 알뜰하게 사용하려면?

CPU는 명령어를 하나씩 처리한다.

명령어가 처리되는 기본적인 과정은 다음과 같다.

```
명령어 인출 → 명령어 해석 → 명령어 실행 → 결과 저장
```

처음에는 하나의 명령어가 모든 과정을 끝낸 후 다음 명령어를 실행한다고 생각하기 쉽다.

하지만 각 단계가 **서로 겹치지 않는다면**, CPU는 여러 명령어의 각 단계를 동시에 처리할 수 있다.

이러한 방식이 **명령어 파이프라인(Instruction Pipeline)**이다.

---

# 2. 명령어 파이프라인

명령어 파이프라인은

> **여러 명령어를 각각의 처리 단계에서 겹쳐 실행하는 기법**

이다.

예를 들어 명령어가 다음과 같은 과정을 거친다고 하자.

```
1. 인출(Fetch)
2. 해석(Decode)
3. 실행(Execute)
4. 결과 저장(Write Back)
```

명령어를 순차적으로 하나씩 처리하면:

```
명령어 1 → 인출 → 해석 → 실행 → 저장
명령어 2                         → 인출 → 해석 → 실행 → 저장
명령어 3                                             → ...
```

하지만 파이프라인을 사용하면:

```
시간 →
명령어 1 : 인출 → 해석 → 실행 → 저장
명령어 2 :        인출 → 해석 → 실행 → 저장
명령어 3 :               인출 → 해석 → 실행 → 저장
명령어 4 :                      인출 → 해석 → 실행 → 저장
```

각 단계가 겹쳐서 실행된다.

따라서 CPU의 여러 부품이 쉬지 않고 일하도록 만들어 **전체적인 명령어 처리량을 높일 수 있다.**

### 💡 핵심

> **파이프라인의 핵심은 하나의 명령어를 더 빨리 끝내는 것이 아니라, 여러 명령어를 겹쳐 처리하여 전체적인 처리량을 높이는 것이다.**

---

# 3. 명령어 파이프라인의 위험

명령어 파이프라인이 항상 성능 향상으로 이어지는 것은 아니다.

파이프라인을 사용하다 보면 명령어를 정상적으로 겹쳐 실행하기 어려운 상황이 발생할 수 있다.

이를 **파이프라인 위험(Pipeline Hazard)**이라고 한다.

대표적으로 세 가지가 있다.

1. 데이터 위험
2. 제어 위험
3. 구조적 위험

---

# 4. 데이터 위험(Data Hazard)

데이터 위험은

> **명령어 간의 데이터 의존성 때문에 발생하는 위험**

이다.

예를 들어,

```
명령어 1 : A를 계산해서 B에 저장
명령어 2 : B의 값을 가져와서 사용
```

두 번째 명령어는 첫 번째 명령어가 B에 값을 저장하기 전까지 제대로 실행할 수 없다.

즉,

```
명령어 1
   ↓
결과 생성
   ↓
명령어 2가 그 결과를 사용
```

처럼 **앞선 명령어의 결과가 뒤의 명령어 실행에 필요한 경우**, 명령어를 마음대로 겹쳐 실행할 수 없다.

이것이 데이터 위험이다.

### 💡 내가 이해한 방식

> **앞 명령어의 결과를 뒤 명령어가 필요로 한다면, 파이프라인을 마음대로 진행할 수 없다.**

---

# 5. 제어 위험(Control Hazard)

제어 위험은

> **프로그램 카운터(PC)의 갑작스러운 변화로 인해 발생하는 위험**

이다.

CPU는 일반적으로 다음에 실행할 명령어의 주소를 프로그램 카운터(PC)를 통해 알 수 있다.

그런데 프로그램 실행 중에

* JUMP
* CALL
* INTERRUPT
* 조건에 따른 분기

등이 발생하면 다음에 실행할 명령어의 주소가 갑자기 변경될 수 있다.

예를 들어 CPU가 다음 명령어를 미리 가져왔는데,

```
명령어 A
   ↓
명령어 B
   ↓
명령어 C
```

실제로는 A에서 특정 주소로 점프해야 한다면,

```
명령어 A
   ↓
JUMP
   ↓
갑자기 다른 주소의 명령어 실행
```

이미 가져온 B, C가 필요 없는 명령어가 될 수 있다.

### 💡 핵심

> **CPU가 다음에 실행될 명령어를 미리 가져왔는데, 프로그램의 실행 흐름이 갑자기 바뀌면 파이프라인에 문제가 생길 수 있다.**

---

# 6. 구조적 위험(Structural Hazard)

구조적 위험은

> **서로 다른 명령어가 동시에 같은 CPU 자원을 사용하려고 할 때 발생하는 위험**

이다.

예를 들어 두 명령어가 동시에 같은 CPU의 특정 부품을 사용하려고 한다면 문제가 발생할 수 있다.

```
명령어 1 ──┐
           ├── 같은 CPU 자원 사용
명령어 2 ──┘
```

CPU의 자원은 무한하지 않기 때문에 여러 명령어가 동시에 같은 자원을 요구하면 충돌이 발생할 수 있다.

### 💡 대표적인 원인

* ALU 등의 연산 장치
* 레지스터
* 메모리 접근 장치 등

---

# 7. 파이프라인 위험 3가지 정리

| 종류     | 원인            | 쉽게 이해하면           |
| ------ | ------------- | ----------------- |
| 데이터 위험 | 명령어 간 데이터 의존성 | 앞 명령어 결과가 필요함     |
| 제어 위험  | 프로그램 실행 흐름 변경 | 다음에 실행할 주소가 바뀜    |
| 구조적 위험 | CPU 자원 충돌     | 같은 부품을 동시에 사용하려 함 |

### 한 문장으로 정리

> **파이프라인 위험은 여러 명령어를 동시에 처리하려 할 때 발생하는 문제이다.**

---

# 8. 슈퍼스칼라(Superscalar)

그렇다면 파이프라인을 여러 개 사용하면 어떨까?

**슈퍼스칼라(Superscalar)**는

> **CPU 내부에 여러 개의 명령어 파이프라인을 포함하여 여러 명령어를 동시에 처리할 수 있도록 만든 구조**

이다.

간단하게 비교하면:

```
일반적인 파이프라인

명령어 → [Pipeline]
```

```
슈퍼스칼라

명령어 1 → [Pipeline 1]
명령어 2 → [Pipeline 2]
명령어 3 → [Pipeline 3]
```

이론적으로는 파이프라인의 개수가 많아질수록 동시에 처리할 수 있는 명령어가 많아진다.

하지만 **파이프라인의 개수에 정확히 비례해서 성능이 증가하는 것은 아니다.**

왜냐하면 파이프라인이 많아질수록

* 데이터 위험
* 제어 위험
* 구조적 위험

등을 관리하는 것이 더 어려워지기 때문이다.

### 💡 핵심

> **슈퍼스칼라는 여러 개의 파이프라인을 이용해 명령어를 병렬적으로 처리하는 구조이지만, 파이프라인을 늘린 만큼 성능이 그대로 증가하는 것은 아니다.**

---

# 9. 비순차적 명령어 처리(OoO)

이번에는 조금 특이한 방법이다.

CPU는 일반적으로 프로그램에 작성된 명령어 순서대로 실행한다고 생각할 수 있다.

그런데 앞선 명령어 때문에 어떤 명령어의 실행이 잠시 막혀 있다면, CPU가 무조건 기다려야 할까?

그럴 필요가 없다.

> **실행에 문제가 없는 뒤쪽 명령어를 먼저 처리하면 된다.**

이것이 **비순차적 명령어 처리(Out-of-Order Execution)**이다.

쉽게 말하면

> **"합법적인 새치기"**

라고 이해할 수 있다.

---

## 🏃 예시

다음과 같은 명령어가 있다고 하자.

```
명령어 1 : A 계산
명령어 2 : 명령어 1의 결과 사용
명령어 3 : C 계산
```

명령어 2는 명령어 1의 결과가 필요하기 때문에 당장 실행할 수 없다.

그렇다면 CPU가 그냥 기다리는 대신,

```
명령어 1 → 실행 중
명령어 2 → 대기

명령어 3 → 실행 가능 → 먼저 실행
```

할 수 있다.

이렇게 하면 CPU의 파이프라인이 불필요하게 멈추는 것을 줄일 수 있다.

---

## ⚠️ 아무 명령어나 순서를 바꿀 수 있는 것은 아니다.

비순차적으로 실행하더라도 **프로그램 전체의 실행 결과에 영향을 주어서는 안 된다.**

즉,

> **실행 순서를 바꾸더라도 최종적인 프로그램 결과가 달라지지 않는 경우에만 순서를 바꿀 수 있다.**

### 💡 내가 이해한 방식

> **비순차적 명령어 처리는 명령어의 실행 순서를 무작정 바꾸는 것이 아니라, 프로그램의 결과에 영향을 주지 않는 범위에서 실행 가능한 명령어를 먼저 처리하는 것이다.**

---

# 10. 05-2 핵심 정리

```
CPU의 명령어 처리 속도를 높이는 방법
              │
              ↓
      명령어 파이프라인
              │
              ├── 여러 명령어를 겹쳐 처리
              │
              ↓
       파이프라인 위험
       ├── 데이터 위험
       ├── 제어 위험
       └── 구조적 위험
              │
              ↓
        슈퍼스칼라
              │
              ↓
     여러 파이프라인 활용
              │
              ↓
    비순차적 명령어 처리
              │
              ↓
   파이프라인이 멈추는 것을
       최대한 줄임
```

# 05-3. 명령어 집합 구조(ISA), CISC & RISC

## 📌 학습 목표

* 명령어 집합 구조(ISA)가 무엇인지 이해하기
* ISA가 CPU와 소프트웨어 사이에서 어떤 역할을 하는지 이해하기
* CISC와 RISC의 특징과 차이 이해하기
* 명령어 집합과 명령어 파이프라이닝의 관계 이해하기

---

# 1. CPU가 이해하는 명령어는 모두 같을까?

앞에서는 CPU가 명령어를 어떻게 빠르게 처리하는지를 살펴봤다.

그렇다면 이번에는 조금 더 근본적인 질문을 해볼 수 있다.

> **CPU가 실행하는 명령어는 어떤 모습으로 만들어져 있을까?**

CPU마다 사용하는 명령어의 형태나 주소 지정 방식 등이 다르다.

즉,

> **모든 CPU가 똑같은 명령어를 사용하는 것은 아니다.**

---

# 2. 명령어 집합 구조(ISA)

**ISA(Instruction Set Architecture)**는

> **CPU가 이해하고 실행할 수 있는 명령어들의 집합이자, CPU와 소프트웨어 사이의 약속**

이다.

쉽게 생각하면 **ISA는 CPU가 사용하는 언어**라고 볼 수 있다.

예를 들어 사람이

```
한국어
영어
일본어
```

등 서로 다른 언어를 사용하는 것처럼 CPU도 어떤 ISA를 사용하는지에 따라 이해할 수 있는 명령어가 달라진다.

---

## 🗣️ ISA를 CPU의 언어라고 생각해보기

```
프로그램
   ↓
컴파일
   ↓
CPU가 이해할 수 있는 명령어
   ↓
CPU 실행
```

같은 소스코드라도 어떤 CPU를 대상으로 컴파일하느냐에 따라 **서로 다른 명령어 형태**로 변환될 수 있다.

따라서 ISA는 단순히 명령어 목록만 의미하는 것이 아니라,

* 어떤 명령어를 사용할 수 있는지
* 명령어가 어떤 형태인지
* 어떤 레지스터를 사용하는지
* 어떤 방식으로 메모리에 접근하는지

등 CPU와 소프트웨어가 상호작용하는 기본적인 규칙을 정의한다.

### 💡 핵심

> **ISA는 CPU의 언어이자 하드웨어가 소프트웨어를 어떻게 이해하고 실행할지에 대한 약속이다.**

---

# 3. ISA의 대표적인 두 가지 흐름

명령어 집합을 설계하는 대표적인 방식으로

* **CISC**
* **RISC**

가 있다.

---

# 4. CISC

**CISC(Complex Instruction Set Computer)**

> **복잡하고 다양한 명령어를 사용하는 방식**

대표적으로 **x86, x86-64 계열**이 CISC 계열 ISA에 해당한다.

### CISC의 특징

#### ✅ 다양한 명령어

하나의 명령어가 여러 작업을 수행할 수 있도록 복잡하게 설계할 수 있다.

따라서 상대적으로 적은 수의 명령어로도 프로그램을 구성할 수 있다.

#### ✅ 가변 길이 명령어

명령어의 크기가 일정하지 않고 다양할 수 있다.

```
명령어 1 → 짧음
명령어 2 → 중간
명령어 3 → 김
```

#### ⚠️ 단점

명령어의 형태와 기능이 복잡하고 다양하기 때문에 명령어마다 실행에 필요한 시간이 달라질 수 있다.

어떤 명령어는 여러 클럭 주기를 필요로 할 수도 있다.

이러한 특성은 **명령어 파이프라이닝을 복잡하게 만드는 요인**이 될 수 있다.

---

# 5. RISC

**RISC(Reduced Instruction Set Computer)**

> **명령어 종류를 단순화하고 규격화하여 사용하는 방식**

CISC와 달리 명령어를 단순하게 설계하는 것을 중요하게 생각한다.

### RISC의 특징

#### ✅ 단순하고 적은 명령어

명령어 하나하나를 단순하게 만든다.

#### ✅ 고정 길이 명령어

명령어의 길이를 일정하게 만드는 경우가 많다.

```
명령어 1 → 같은 길이
명령어 2 → 같은 길이
명령어 3 → 같은 길이
```

이렇게 하면 CPU가 명령어를 해석하고 파이프라인에 넣기가 상대적으로 수월해진다.

#### ✅ 레지스터 적극 활용

메모리에 직접 접근하는 것을 최소화하고 레지스터를 적극적으로 활용한다.

대표적으로 **Load / Store** 방식이 있다.

```
메모리
  ↕
Load / Store
  ↕
레지스터
  ↕
CPU 연산
```

---

# 6. CISC vs RISC

| 구분       | CISC               | RISC                      |
| -------- | ------------------ | ------------------------- |
| 기본 개념    | 복잡하고 다양한 명령어       | 단순하고 적은 명령어               |
| 명령어 길이   | 가변 길이              | 고정 길이인 경우가 많음             |
| 주소 지정 방식 | 다양한 방식             | 상대적으로 적은 방식               |
| 명령어 수    | 적은 명령어로 작업 가능      | 같은 작업에 더 많은 명령어가 필요할 수 있음 |
| 메모리 접근   | 상대적으로 다양한 명령어에서 가능 | Load / Store 중심           |
| 레지스터 활용  | 상대적으로 제한적          | 적극적으로 활용                  |
| 파이프라이닝   | 상대적으로 복잡           | 상대적으로 유리                  |

---

# 7. CISC와 RISC는 완전히 반대일까?

처음 공부하면

> CISC = 나쁜 방식
> RISC = 좋은 방식

처럼 생각하기 쉽지만, 그렇게 단순하게 구분할 수는 없다.

각각 장단점이 있고 현대 CPU에서는 서로의 장점을 활용하는 방향으로 발전해왔다.

특히 현대의 CISC 계열 CPU는 복잡한 외부 명령어를 내부적으로 더 작은 단위의 명령어로 나누어 실행하는 방식 등을 활용한다.

즉, 겉으로는 CISC 계열 ISA를 사용하더라도 **CPU 내부에서는 파이프라이닝과 병렬 처리를 효율적으로 수행하기 위한 여러 기법을 사용할 수 있다.**

### 💡 내가 이해한 방식

> **CISC와 RISC를 단순히 "복잡한 CPU vs 단순한 CPU"로 이해하기보다는, CPU가 이해하는 명령어를 어떤 철학으로 설계했는지의 차이로 이해하는 것이 좋다.**

---

# 8. 명령어 파이프라이닝과 CISC / RISC

앞에서 배운 **명령어 파이프라인**과 CISC/RISC는 서로 연결되어 있다.

파이프라인에서는 여러 명령어를 겹쳐 처리해야 하기 때문에 **명령어를 일정하고 예측하기 쉽게 만드는 것**이 유리하다.

RISC는

* 단순한 명령어
* 일정한 형식
* 고정 길이 명령어
* 레지스터 중심의 연산

등을 활용하기 때문에 파이프라이닝에 상대적으로 유리하다.

반면 CISC는

* 복잡한 명령어
* 다양한 명령어 형식
* 가변 길이 명령어

등으로 인해 파이프라이닝을 구현하는 것이 상대적으로 복잡할 수 있다.

# 9. ⭐ 이번 단원에서 내가 가져갈 핵심

이번 단원에서 가장 중요한 연결은 다음과 같다.

```
CPU 성능 향상
      ↓
명령어를 겹쳐 실행
      ↓
명령어 파이프라인
      ↓
파이프라인 위험 발생
      ↓
슈퍼스칼라 / 비순차적 명령어 처리
      ↓
더 많은 명령어를 효율적으로 처리
```

그리고 CPU가 이해하는 명령어 자체에도 설계 방식이 있다.

```
CPU가 이해하는 명령어
        ↓
ISA
        ↓
┌───────────────┐
│               │
CISC           RISC
│               │
복잡한 명령어    단순한 명령어
가변 길이       고정 길이
```

---

# 💡 한 문장으로 정리

> **CPU는 명령어 파이프라인, 슈퍼스칼라, 비순차적 명령어 처리 등을 통해 여러 명령어를 효율적으로 병렬 처리하며, CPU가 이해하는 명령어의 규칙인 ISA는 CISC와 RISC와 같은 방식으로 설계될 수 있다.**
